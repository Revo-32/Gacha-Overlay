# M9.12 — Static memory / resource lifetime audit

## Scope and baseline

Baseline: M9.11 Remote-only, 1,184 Debug / Release tests. M9.10 UIA and
M9.11 Local RPC / legacy OAuth remain retired. No new source selection,
branding, UI overhaul, deployment, release, automatic telemetry or long soak.

M9.11 actual five-cycle test was user-confirmed (cycle 0 + five restarts), with
six distinct backend epochs and no observed duplicate state. Its 225.132-second
capture reported WPF WS average 281.822 MiB, private average 220.053 MiB and
private growth +23.107 MiB / +11.195% (Possible Growth). This is neither proof
of a leak nor proof of a fix. M9.11 Quick was a different run (66.135 seconds,
WS 272.717 MiB, private 189.909 MiB). Do not compare them as a controlled trial.

## Findings and narrowly scoped corrections

| Finding | Ownership path / impact | Severity | Disposition |
| --- | --- | --- | --- |
| Per-connection requests outlived reconnect | Switch used application token; Sales resync used session-loop token; requests could keep a retired client/bootstrap alive | Medium | Fixed: connection request scope, at most one switch/resync/action each; cancel and join before client disposal; reject late results |
| Naturally completed session CTS overwritten | Linked cancellation registration survived a subsequent Start | Medium | Fixed: cancel/dispose completed session's CTS before replacement; stop disposes in finally |
| Exceptional bootstrap exit did not join all siblings | Stale Chat bootstrap or synchronous bootstrap failure could leave Presence/Sales tasks running and publishing | Medium | Fixed: unconditional cancellation/drain, cancellation check before publication |
| Initial bootstrap retained by long-lived async frames | Initial recent20 / Sales task results could stay rooted after later replacements | Low | Fixed: remove forwarding-only async frames and release settled bootstrap references before stream await |
| Cache load admission unbounded | Completed cache was bounded but concurrent unique loads were not; Clear hid old outstanding work | High under stalled/high-churn media | Fixed: loader admission bounded to cache capacity, including retired generations; excess request returns fallback without another queue or cooldown |
| Body reads not covered by HttpClient header timeout | ResponseHeadersRead can finish headers while body stalls and owns streams/buffers/tasks | Medium | Fixed: 10-second linked deadline covers headers and body, canceled by service shutdown; synchronous decode remains separately bounded by input size |
| WPF StreamSource retains encoded MemoryStream buffer | OnLoad/Freeze closes decoder use, but the StreamSource object can still own encoded bytes | Medium | Fixed: releasing stream wrapper disconnects encoded buffer after decode; decoded pixels unchanged |
| Detached text/chat/sales views remained subscribed | Long-lived token/VM publisher could retain old visual tree after unload | Medium | Fixed: unload detaches, reload attaches exactly once; chat aborts pending scroll; text disposes native layout |
| Sales failure map never pruned when message leaves window | Each failed ID could accumulate beyond current Sales state | Medium | Fixed: pending/failure entries retired against current evidence/action targets; pending confirmation settled |
| Backend unfinished work not bounded by completed caches | Authorization refreshes and Sales actions could survive cache eviction or cancellation of a caller | Medium | Fixed: 128 outstanding authorization refreshes / 256 unfinished actions; fail closed on overload |
| Enlarged preview retained after clear/shutdown | One preview could retain an image outside cleared media ownership | Low | Fixed: clear preview reference on cache clear and coordinator disposal |

The first pre-fix tests reproduced 20 outstanding loads in a capacity-2 cache
and one surviving token event handler after Unloaded. Cache ownership tests do
not force GC or claim native heap collection. The bitmap test checks that the
wrapper has no source reference and compares decoded BGRA pixels exactly.

## Reconnect, events, tasks and cancellation inventory

- `LSOverlayRemoteClient`: socket and send semaphore scoped with using; linked
  switch/resync pumps canceled and joined in finally; response/request/content
  streams disposed with using/await using; receive ArrayPool buffer returned.
  Transactional Chat requests cap at five, staged events at 256 each; commit
  clears request/staged dictionaries. Sales holds one current bootstrap plus
  at most 256 staged events, replaced/cleared on new resync.
- `RemoteChatProductionCoordinator`: process CTS; one session CTS; pairing CTS
  disposed by its async owner; bootstrap CTS per attempt; auxiliary request scope
  per connection; Sales action has a linked per-request caller token. Pairing
  cancellation now stays under the same lock as removal, avoiding cancel/dispose
  races. Per-client listeners and ingress adapter are detached on retirement.
  Completed tasks are not accumulated. Retry delay is after old-resource cleanup.
- `RemoteChatIngressAdapter`: exactly two client subscriptions removed in Dispose;
  stale generation is rejected. The transport owns staging; initial core bootstrap
  is synchronous, followed by transactional ReplaceMain. The generic core live
  buffer / unbounded-default Sales store are legacy-compatible primitives, not
  asynchronous production Remote staging or the production Sales store.
- `BackendWebSocketSession`: subscription, per-connection bounded outbound queue,
  forwarding/send/receive/heartbeat tasks; linked cancellation joins tasks.
  Chat switch gate cancels/drains old subscription pump and disposes CTS.
  Sales resubscribe does the same. ASP.NET endpoint owns socket and connection
  lease. Subscriber registries remove closed connections.
- Backend Gateway subscribes once; Stop detaches and drains admitted callbacks
  before logout. Canonical refresh coalescer retains at most 256 tasks, removes
  entries in finally; request cancellation does not abort a shared refresh.
  Backend action/authorization work is shared and intentionally not canceled by
  one HTTP caller. New independent admission caps bound this ownership.
- Media enrichment is bounded one-shot work, caller canceled on message revision,
  settings reload or message disposal. Shared downloads continue within capacity
  and deadline, and only current identity may apply results. Forward uses the same
  emoji/thumbnail/sticker services, no per-forward cache added.
- Async command execution is serialized by the command; notification preparation
  is a short one-shot disk task, with request version checked before dispatcher
  playback. Sales confirmation wait is capped at 10 seconds and evicted pending
  state now settles early. Diagnostics export is single-flight, bounded I/O.

## WPF ownership and timers

- Settings is intentionally cached as one hidden window by SettingsWindowService;
  user X hides it, app exit closes it. Foundation VM and its Remote settings VM
  are process-owned and detach localization on disposal. No new window per open.
- Onboarding has one current window/VM; Closed detaches handler, disposes VM and
  clears host fields. Sales preview VM detaches localization on Closed. Product
  mapping window/VM are created together, no singleton publisher subscription;
  CollectionViewSource filter references its own window-owned collection/VM.
- Queue Detail is an in-HUD panel, not a growing collection of windows.
  SalesQueueView and ChatView now detach their VM callbacks on unload. Self-owned
  Loaded/Unloaded/DataContextChanged handlers do not create an external GC root.
- CrispOutlinedText releases TextLine/TextFormatter layout on invalidation/unload;
  old token collection/property listeners are removed before reattach.
- WindowPlacementService: one dispatcher debounce timer; Stop + Tick detach on
  Dispose, geometry/display callbacks detached. GameForegroundMonitor: one WinEvent
  hook or one 1-second fallback timer; mode change/disposal unhooks/disposes it.
- RemoteRecoveryAudit: one opt-in 1-second timer per WPF process, none on normal
  launch; locked disposed check prevents post-dispose publication. It stores one
  snapshot and no history. Existing M9.11 tests cover stale/ended audit attempts.
- Backend heartbeat has one PeriodicTimer per WebSocket; active-channel eviction
  has one hosted PeriodicTimer, both token-scoped. DeveloperShutdownWatcher
  detaches/disposes its FileSystemWatcher. No reconnect creates a permanent timer.
- UI updates are coalesced in HudWindowController and Sales presentation. Small
  Presence/status dispatcher posts remain event-driven one-shots; no replay list
  is retained. Dispatcher blockage is not claimed tested for arbitrary durations.

## Data and bounds

Current inventory: `m99-runtime-bounds.json`, updated for M9.12 with UIA removed.
Chat 20, canonical Sales/evidence 30, Sales tombstones 256, host slots 2. Canonical
replacement removes old messages, observations and detail items. Bounded journals
intentionally retain limited mutation history for resumable delivery; an evicted
visible message may therefore still exist in the bounded server journal.

Media: decoded cache 64 emoji / 24 thumbnail / 24 sticker, same per-class failure
and in-flight caps (including cleared generations). Each download at most 12 MiB.
Decode width stays 64 / 384 / 384; no quality setting lowered, no new cache, no
animated-media feature. WPF/native decoder memory is not fully represented by
managed cache membership or the decoded-size estimate. A count bound is not a
guarantee of a low absolute peak, especially for unusual image aspect ratios.

Other fixed-cardinality structures: authorization invalidation versions have one
configured Guild in production; runtime metric names are fixed constants, each
duration ring 256; Backend counters are enum-indexed. Auth credentials/pairings
128/64, active connections 64 globally / 2 per installation. SDK message cache is
0; there is no broad member download. Configuration/catalog data is user-owned
configuration, not event-history accumulation.

## Static mutable references / DI / disposable owners

- `AppSettings.EmptyScrollPositions`: one empty dictionary, only used as the
  empty source fallback; settings updates create copied dictionaries. No runtime
  append to this static instance.
- `TransportAuthentication.ForbiddenQueryKeys`: fixed four-element private set,
  lookup only. Retry delay arrays, font fallbacks, theme definition/swatches and
  DPAPI entropy are fixed initialization-time values; no event/history append.
- Static JsonSerializerOptions (protocol/settings/product/credential serialization)
  are reused per contract; serializer metadata caching is intentional and limited
  to finite product types. DependencyProperty registration and immutable default
  snapshots are framework/process lifetime. No mutable static message cache or
  static application event added. App global exception handlers detach on exit.
- WPF manually owns its process services through ApplicationHost; short-lived
  UI subscribers detach. Backend DI singletons are intentional shared state;
  hosted services stop with host; DI owns DiscordSocketClient. No transient UI
  service registered into a Backend singleton.
- Ownership chain: ApplicationHost -> Remote coordinator/audit, sales coordinator,
  sound, settings service/Foundation VM, tray and HUD controller. HUD -> chat/media,
  coalescer, placement, hotkeys, foreground monitor, modifier hook, interop.
  Interop only detaches its borrowed HwndSource hook (does not dispose WPF's source).
  App owns its single-instance Mutex; logger closes writer/file stream at rotation
  and exit; per-request HTTP/file/memory streams use structured disposal.
- Backend action stripe SemaphoreSlim[64] is process-fixed, async-only with no
  WaitHandle access; no additional IDisposable introduced just for managed gates.
- Sound owns at most one MediaPlayer; previous playback Stop/Close before replace,
  MediaEnded/MediaFailed Close it, disposal closes it. Player-owned lambdas form
  self-contained collectible cycles, not subscriptions to an immortal publisher.
  No external player list; generated WAV asset names are two fixed files. No sound
  test notification sent to production Discord by automation.

## Future RC methodology (documented only)

After 2.0 RC, use multiple PCs/users for 4–5-hour real gameplay sessions. Record
local CPU, WS/private bytes, handles, threads, GDI/USER, runtime, reconnect and
Sales-resync counts. Note warmup, representative media/chat churn, channel switches,
settings cycles and recovery periods. Compare post-warmup trend and repeated workload
plateaus, not only initial/final values; investigate persistent monotonic growth.
Never record message bodies, Sales content, raw Discord/Host IDs or tokens. Export
locally and share manually after sanitization; no automatic telemetry upload.

Linux runtime/deployment verification, final release engineering, branding and
the 2.0 UI/UX backlog remain deferred. Do not start the next milestone automatically.
