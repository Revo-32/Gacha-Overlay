# M9.1 Discord Bot Backend Foundation

## Scope

M9.1 converts `LSOverlay.Backend` from the M9.0 compile-time boundary into an
independently runnable, headless .NET 8 process. It logs into Discord through the
officially supported Bot flow, observes the configured Guild through one Gateway
connection, normalizes a deliberately small event surface, and keeps that surface
in a bounded in-memory journal.

There is deliberately no Backend-to-Windows transport in M9.1. `GachaOverlay.App`
does not reference, connect to, or launch this executable. The published Windows
runtime continues to use Discord Local RPC for chat and UI Automation for sales
completion evidence.

## Discord.Net selection and API audit

Only `LSOverlay.Backend` references `Discord.Net.WebSocket`, pinned to version
`3.20.1`. This focused package supplies the socket client and its required REST
login dependency without adding the broad `Discord.Net` meta-package. It provides
Discord's reconnect implementation, typed event payloads, Bot authentication, and
graceful client start/stop behavior; no parallel raw Gateway client exists.

The installed 3.20.1 assemblies are protected by compile-time and reflection
regression checks. The audit confirms:

- forwarded messages: `IUserMessage.ForwardedMessages` and
  `MessageSnapshot.Message`;
- sticker metadata: `IMessage.Stickers`;
- attachments, embeds, and components: the corresponding `IMessage` collections;
- replies: `IUserMessage.ReferencedMessage`;
- polls: `IUserMessage.Poll` exists for future message normalization.

M9.1 records only safe counts/identity metadata, not final rendering DTOs. Poll
vote events are out of scope, so `GuildMessagePolls` is not requested. Automatic
sticker resolution and default sticker downloading are disabled to avoid
background REST amplification.

## Process and lifecycle

The project is a `net8.0` executable built on .NET Generic Host and a single
`BackgroundService`. It is platform-neutral: no WPF, Windows target framework,
ASP.NET Core server, database, Docker, or Railway configuration is present.

One `DiscordSocketClient` is created through dependency injection. Startup is
single-use; Discord.Net owns supported reconnection. Ctrl+C and SIGTERM flow
through Generic Host cancellation, followed by `StopAsync`, `LogoutAsync`, event
unsubscription, dependency disposal, and a final aggregate counter snapshot.

Connection health uses thread-safe, deduplicated transitions:

- `Stopped`
- `Starting`
- `Connecting`
- `Ready`
- `TargetGuildUnavailable`
- `Disconnected`
- `Faulted`

Sanitized reasons distinguish startup, Gateway readiness/disconnection, target
Guild absence, privileged-intent rejection, authentication failure, unexpected
failure, and graceful shutdown. No polling loop or application reconnect loop is
used.

## Configuration and secret policy

Runtime configuration is environment-only:

- `LSO_DISCORD_BOT_TOKEN` — required secret;
- `LSO_DISCORD_GUILD_ID` — required target Guild ID;
- `LSO_TRACKED_HOST_IDS` — optional comma/semicolon-separated host IDs.

Tracked IDs are trimmed, validated as non-zero Discord IDs, deduplicated in input
order, and limited to 16. Documentation and tests use synthetic values only, such
as `111111111111111111`.

The Bot token is wrapped in a credential object whose string representation is
always `[REDACTED]`. It is revealed only at the Discord.Net login call. It is not
accepted as a command-line argument, written to `appsettings.json`, stored in the
journal, sent to the Windows client, or intentionally included in logs or
exceptions. Missing token or malformed non-secret configuration fails before Host
startup with a short actionable message and non-zero exit code. Authentication
failures log only a sanitized exception category.

For local validation, `tools\dev\run-ls-backend-local.ps1` prompts for the token
using `Read-Host -AsSecureString`, prompts for missing non-secret values, sets
process-scoped variables only for the child run, and clears all three variables in
`finally`. No token literal is placed in PowerShell history or on the process
command line.

## Gateway and permission policy

The exact requested intent mask is:

- `GatewayIntents.Guilds`
- `GatewayIntents.GuildMessages`
- `GatewayIntents.GuildMessageReactions`
- `GatewayIntents.MessageContent`
- `GatewayIntents.GuildPresences`

`GuildMembers` is off. Direct messages, typing, voice, moderation, webhooks,
invites, integrations, and poll-vote intents are also off. Presence Intent and
Message Content Intent must be enabled in the Discord Developer Portal.

Socket configuration uses `MessageCacheSize = 0`,
`AlwaysDownloadUsers = false`, `AlwaysDownloadDefaultStickers = false`, and
`AlwaysResolveStickers = false`. Discord.Net may maintain the minimum internal
Gateway state required by its implementation, but LS Overlay does not create a
member or untracked-presence cache.

After Ready, a read-only audit examines effective permissions without changing
roles or channels. The expected channel permissions are View Channel and Read
Message History, plus Add Reactions for a future milestone. Add Reactions is not
exercised in M9.1. Administrator, management permissions, and Send Messages are
flagged as excessive; the Backend never uses them. Channel names and message
content are not logged.

## Guild and event privacy boundary

`LSO_DISCORD_GUILD_ID` defines one hard privacy boundary. Message and reaction
events are accepted only when their cached Gateway channel belongs to that Guild.
Presence processing checks the tracked-host set first, then requires the matching
Guild user. Events from another Guild are counted as filtered and are not added to
application state or the journal.

Normalized Backend-owned events contain only stable evidence:

- message create/update/delete (including bulk deletes as individual identities):
  Guild, channel, message, optional author, timestamps, and feature counts;
- reaction add/remove/clear-all/clear-emoji: Guild, channel, message, optional
  user, optional custom emoji ID/name, and operation;
- tracked presence: configured host identity, Discord status, GTA activity/session
  flags, structured current/maximum players, and observation timestamp.

Discord.Net socket types do not cross into Core, Infrastructure, the Windows App,
or future transport contracts. Raw Gateway JSON and message bodies are never
retained. M9.1 observes reactions only; it does not mutate Discord and does not
call `SalesStateEngine`.

## GTA Rich Presence

The first verified profile is explicit and extensible:

- display label: `Grand Theft Auto V Enhanced`;
- primary application ID: `1329870933695135785`;
- activity type: `Playing`;
- exact ordinal state: `GTA Online`.

An online GTA session additionally requires structured `RichGame.Party` values:
members must be at least zero, capacity must be greater than zero, and members
must not exceed capacity. A verified `11 / 32` payload therefore maps exactly to
current 11, maximum 32. Missing or invalid party values are unavailable; values
are never clamped or guessed. There is no regular expression or parsing of free-
form activity state/details. Future GTA Legacy support requires another verified
profile and application ID rather than a parsing heuristic.

Application code reads only application ID, name, activity type, state, and party
members/capacity. It does not access or model Rich Presence join, spectate, or
match secrets.

At Ready, the Backend attempts to use currently available Discord.Net Guild state
for each configured host. A host absent from that cache remains
`AwaitingPresence`; this is not an error and does not trigger a member download or
poll. `PresenceUpdated` later updates it. Untracked user events are discarded
before activity mapping and create no durable state. The application-owned store
is fixed to at most the 16 configured identities.

Presence changes are semantically deduplicated. Repeated `11 / 32` does not add a
journal entry; `11 / 32` to `12 / 32`, or GTA Online to no matching activity,
adds exactly one normalized change.

## Journal, metrics, and logging

The Backend journal is an in-memory, lock-protected ring of 2,048 normalized
events. It reuses M9.0 `OverlayEventPosition`: protocol version, monotonically
increasing event sequence, and one non-negative process generation. Overflow
overwrites the oldest entry. There are no consumers or slow-consumer waits yet,
and the journal stores no SDK payload, token, Rich Presence secret, or entire
member object.

Fixed process-local atomic counters cover connection, messages, reactions,
filtering, presence receipt/matches, structured party availability, and normalized
changes. There is no telemetry upload, high-cardinality label, periodic metrics
task, or user-ID metric dimension. Significant lifecycle and permission results
are Info/Warning messages; individual message, reaction, and untracked presence
events are not Info-logged. The final shutdown snapshot exposes aggregate counts
without content.

## Live validation

Automated tests do not open a network connection. For a user-authorized local
check, run this from the repository root:

```powershell
tools\dev\run-ls-backend-local.ps1
```

Enter the target Guild ID, optional tracked host IDs, and securely prompted Bot
token. The existing Bot/Application is sufficient. The Developer Portal must have
Presence Intent and Message Content Intent enabled; Guild Members Intent and
Administrator permission are not needed.

Expected sanitized output includes Backend starting, Discord connecting/ready,
target Guild availability, tracked-host count, and either `Host[1]: GTA Online 11
/ 32` or `Host[1]: Awaiting Presence`. After sending test message/reaction events,
press Ctrl+C to see aggregate counters. Do not paste the Bot token into reports or
chat.

## Deliberately deferred

M9.1 has no HTTP or WebSocket server/client, pairing/authentication protocol,
remote bootstrap/replay, complete message/rendering normalization, Windows sticker
or forward rendering changes, remote channel selection, Session HUD, sales buttons,
reaction write-back, notification sound, database, media proxy, Railway/Docker
deployment, Local RPC/UIA/OAuth retirement, executable/project/namespace rename,
repository rename, or GitHub release action.

M9.2 should design a dedicated Backend-to-Windows transport/protocol boundary,
authentication and bootstrap/replay behavior. A small `LSOverlay.Protocol` project
is likely cleaner than exposing Backend or Discord.Net types to Core, but it should
be introduced only with the concrete M9.2 contract. The legacy providers must stay
available until the authenticated remote path is verified.
