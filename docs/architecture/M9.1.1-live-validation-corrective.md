# M9.1.1 Live Validation Corrective

## Live evidence and scope

The first user-authorized M9.1 run confirmed real Bot login, Gateway readiness,
target Guild resolution, 32 message events, 3 reaction events, and 137 presence
events. It also exposed two local-lifecycle defects: the optional tracked-host
prompt was skipped, and normal Ctrl+C shutdown reported an
`ObjectDisposedException`.

M9.1.1 changes only process shutdown ownership and the local validation helper.
Gateway intents, permission policy, message/reaction normalization, GTA profile,
Windows runtime composition, and Sales behavior are unchanged.

## ObjectDisposedException root cause

`HostingAbstractionsHostExtensions.RunAsync` stops and disposes the Host before its
returned task completes. M9.1 awaited `host.RunAsync()` and then tried to resolve
`BackendConnectionHealth` from `host.Services`. At that point the DI
`ServiceProvider` had already been disposed, so the post-run service lookup threw
`ObjectDisposedException`. The additional `using var host` also expressed a second
application-level owner even though `RunAsync` already owns Host disposal.

M9.1.1 captures a small `BackendProcessExitState` holding the health reference
before `RunAsync`. After shutdown it reads only that retained, non-disposable state;
it never re-enters the disposed service provider. `RunAsync` is now the sole Host
disposal owner.

## Gateway teardown ordering

The worker remains the one active Gateway lifecycle owner. Its `finally` block
awaits one shared adapter stop task, reads final process-local metrics, then moves
health to `Stopped/GracefulShutdown`. Duplicate/overlapping stop calls receive the
same task.

The adapter sets its stopping gate and closes a callback-drain gate before SDK
teardown. It detaches application handlers, waits without polling or sleeping for
any normalization callback that already entered the boundary, then calls
Discord.Net logout. Consequently Discord.Net virtual `GuildUnavailable` events
during teardown cannot be presented as an operational target-Guild failure, and
no Backend callback can begin using Discord objects after teardown starts. Generic
Host DI performs the one final `DiscordSocketClient` resource disposal.

No broad `ObjectDisposedException` catch was added. A genuine shutdown failure is
still observable and produces a non-zero process result.

## Local helper correction

An unbound PowerShell `[string]` parameter can appear as an empty string rather
than `$null`. The previous `$null -eq $TrackedHostIds` test therefore skipped the
prompt in the normal no-argument flow and propagated an empty host list.

The helper now uses
`$PSBoundParameters.ContainsKey('TrackedHostIds')` to distinguish an explicitly
provided value from an omitted parameter. With no arguments it always prompts for:

- target Discord Guild ID;
- optional tracked Host Discord User ID(s);
- Bot Token through `Read-Host -AsSecureString`.

One ID or multiple comma/semicolon-separated IDs are passed unchanged through
the process-scoped `LSO_TRACKED_HOST_IDS` environment variable. Backend parsing
remains the source of truth. All three variables are cleared in `finally`; the
token remains absent from command-line arguments, output, source, and disk.

