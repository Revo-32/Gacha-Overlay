# M9.8 GTA Session HUD and Sales turn notification

> Current policy note: M9.8.1 narrows Session presentation to one explicitly
> selected Host 1 or Host 2 slot per client. There is no Auto, Both, or fallback
> mode; settings schema 15 persists the selection and defaults migration to Host 1.

## Scope

M9.8 presents the existing normalized GTA Online Rich Presence feed in the integrated WPF HUD and adds a local, one-shot sound for trusted personal Sales queue transitions. It adds no Discord acquisition path, Gateway, polling timer, REST poll, Voice connection, Bot message, or system notification.

## Session pipeline

The existing production path remains authoritative:

```text
Discord Gateway
  -> GtaPresenceNormalizer
  -> TrackedHostPresenceSnapshot
  -> authenticated Remote publication
  -> LSOverlay.Protocol HostPresenceSnapshot
  -> LSOverlay.RemoteClient
  -> SessionHudViewModel
```

`RemoteChatProductionCoordinator` starts Presence, channel-catalog/Chat, and Sales HTTP bootstrap work concurrently. Each completed canonical result is published independently: delayed Presence cannot hold back Main Chat or Remote Sales, delayed Sales cannot hold back Presence or Chat, and delayed Chat cannot hold back the other two. The authenticated user identity joins Chat and Sales when Presence becomes available without replaying a startup Sales notification. The existing combined WebSocket starts only after the three resume cursors required by that transport are available.

The WPF model uses only `HostSlot`, normalized state, current players, and maximum players. It orders slots deterministically and bounds display to 16. Raw Discord IDs, activity payloads, and Rich Presence secrets never enter the view model.

## Session presentation rules

- A valid `GtaOnline` state requires structured Party values satisfying `current >= 0`, `maximum > 0`, and `current <= maximum`.
- Invalid data is unavailable; it is never parsed from text or clamped.
- Offline, activity removal, invalid Party, canonical host removal, and an empty canonical bootstrap clear stale occupancy.
- Reconnect retains the last snapshot internally but presents `Reconnecting`, preventing a fabricated Offline flicker and preventing stale occupancy from looking live.
- A canonical bootstrap is shown immediately; it does not require a transition.
- One active host uses a compact single row. Multiple hosts use stable `Session {HostSlot}` rows.
- Minimal and UltraCompact layouts retain only valid occupancy and remove labels/chrome.
- `ShowGtaSession` defaults on, is persisted in settings schema 14, and the feature hides when Remote is not selected.
- The Session area has no controls. Existing HUD locking and global click-through remain authoritative.

## Sales notification semantics

The sound observer runs after the existing coalesced `SalesStateEngine` presentation update. It derives only three personal positions: Waiting, Next, and Current.

- The first trusted runtime position establishes a silent baseline.
- A late authenticated-user identity refresh re-establishes that baseline silently.
- `Waiting -> Next` requests one Next sound when enabled.
- `Next/Waiting -> Current` requests one Current sound when enabled.
- Repeated same positions are silent.
- Untrusted/recovering snapshots do not reset the baseline.
- Any effective provider handoff establishes the new position silently, so UIA/Remote recovery cannot replay a turn.
- Manual M9.7 write-back produces a sound only if its resulting canonical queue state genuinely moves the user into Next or Current.

Settings schema 14 adds `SalesTurnSoundEnabled`, `SalesTurnSoundVolume` (0–100, default 50), `NotifySalesNext`, and `NotifySalesCurrent`. The Sales settings page also provides a local Test sound action.

## Audio implementation

The project owns two short synthetic PCM/WAV chimes generated from source code. No GTA, Rockstar, Discord, downloaded, or third-party audio is used. Assets are generated asynchronously into the application's local data directory, so the UI Dispatcher, Remote receive path, Discord ingestion, and Sales engine are never blocked by file generation.

`MediaPlayer` performs non-blocking local playback with application-only volume. Same-kind overlap is suppressed for the short playback duration; Current supersedes Next and Next cannot interrupt Current. Missing devices, file failures, and playback failures are logged once and never affect Chat or Sales.

Because WAV data is generated by compiled application code, the feature works in the self-contained win-x64 single-file publish without an externally copied asset.
