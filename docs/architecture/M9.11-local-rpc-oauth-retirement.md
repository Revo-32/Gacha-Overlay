# M9.11 Local Discord RPC + Legacy OAuth Retirement

## Decision

M9.11 removes the final Local Discord RPC compatibility path and its legacy OAuth flow. The production path is now:

```text
Discord
  -> LSOverlay.Backend
  -> authenticated LS Overlay Remote Protocol
  -> LSOverlay.RemoteClient
  -> GachaOverlay.App (Windows WPF)
```

Main Chat, Sales, Presence, and Sales reaction write-back all use this path. No Local/Remote source arbitration remains. The deferred LS Overlay 2.0 UI/UX backlog is intentionally untouched.

## Retired Local RPC inventory

The following application-owned responsibilities were removed rather than disabled:

- Discord IPC named-pipe transport, framing, handshake, RPC client, and client factory
- local RPC connection/reconnect coordinator and delay policy
- local guild/channel discovery, subscription, bootstrap, and message normalization source
- local Forward resolver that depended on opaque RPC payloads
- Local Main Chat provider selection and compatibility fallback
- Local RPC health/status propagation, diagnostics fields, and metrics
- Discord Desktop process detection and auto-launch service
- Local RPC startup, callback drain, pipe close, and shutdown branches
- tests and development helper code dedicated only to those implementations

Transport-independent message presentation remains: recent-20 ordering, Create/Update/Delete, guild display-name policy, custom emoji, sticker, attachments, Forward snapshots, replies, embeds, polls, Components V2, and bounded media behavior.

## Retired Legacy OAuth inventory

The removed OAuth implementation existed only to authorize Discord Desktop Local RPC. It used:

- a user-provided Discord Application / Client ID and Client Secret
- a configured redirect URI and RPC-related scopes
- the Local RPC `AUTHORIZE` operation
- authorization-code exchange and refresh-token handling
- protected Client Secret and OAuth access/refresh-token persistence
- OAuth setup/re-authentication UI, onboarding, status, diagnostics, and tests

It is not the Remote authentication model and is not retained as a fallback.

## Preserved Remote authentication

M9.11 preserves all current Remote security boundaries:

- Discord Bot Token exists on Backend only
- short-lived pairing claim secret
- per-installation authenticated Remote access token
- Windows CurrentUser DPAPI protection for the Remote credential
- installation identity and authenticated Discord user identity
- Guild/channel authorization and Sales ownership authorization

Remote Bearer authentication is not legacy Discord OAuth.

## Credential retirement policy

At application startup, the retirement service checks only these exact legacy files in the product data directory:

- `discord-client-secret.dat`
- `discord-oauth-token.dat`

If present, each exact file is deleted. There is no wildcard or directory-wide cleanup. Failures are logged by credential file kind and exception type without credential content and do not crash startup. Repeating cleanup is safe.

The following current files are explicitly outside that cleanup:

- `remote-access-token.dat`
- `remote-installation-id.txt`
- settings, product mappings, logs, media cache, and unrelated files

Tests place legacy fixtures beside a byte-identical Remote token fixture, run cleanup twice, and verify the Remote token and unrelated file remain unchanged.

## Settings migration

The persisted settings schema moves from 16 to 17. Loading schema 16:

- maps the retired Server settings category to Discord
- removes the retired Server scroll-position entry
- removes obsolete Local/Remote source selection, legacy Discord Application/channel IDs, redirect URI, and Discord auto-launch fields
- preserves Remote Backend endpoint and selected channel
- preserves Host selection, Sales notification settings, HUD settings, and unrelated future extension fields
- persists through the existing validated atomic replace and backup recovery path

An installation previously set to Local therefore becomes Remote-only. With a valid Remote credential it connects normally; without one it enters the existing pairing-required flow. It never recreates legacy OAuth.

## Failure and privacy behavior

- Transient Backend/network failure preserves last trusted Chat and Sales state and reconnects with bounded backoff.
- Definitive authentication/access rejection clears Chat and Sales message ingress, disables write-back, and exposes pairing/authorization remediation only.
- No Local provider is attempted in either case.
- Diagnostic export continues to reject legacy credential filenames, Remote access-token material, authorization headers, and raw credentials.

## Runtime independence

The WPF composition has no Discord process locator, launcher, IPC endpoint, named-pipe transport, or Local OAuth service. Normal Chat, Sales, Presence, write-back, and notification operation therefore does not wait for or require Discord Desktop. The M9.11 user helper asks the user to close Discord Desktop themselves and never terminates an unknown process.

The updated Reconnect helper now:

- keeps the same WPF process alive through an initial baseline and five Backend restarts;
- reads opt-in, helper-owned WPF evidence for chat snapshot application, chat stream readiness, presence bootstrap publication, presence stream Live, complete Sales bootstrap, and Sales stream readiness;
- requires Sales Tracking ON; an empty but complete Sales queue is valid, while partial or unavailable Sales is not;
- validates the current run, WPF process ID, a heartbeat no older than five seconds, and a hashed Backend publication generation that differs from the preceding restart;
- resets readiness for a new connection attempt, degradation, partial Sales, ended attempts, and pending chat selection; late callbacks from an older attempt cannot satisfy the current gate;
- requires ten continuously ready seconds and an explicit `PASS` from the user at the baseline and after each restart (case-insensitive, with surrounding whitespace trimmed);
- rechecks the same attempt and Backend epoch after user confirmation, so a lost connection during the prompt cannot pass;
- stops before the next restart on `FAIL`, a non-PASS answer, authentication/terminal failure, an exited process, or the 120-second WPF recovery deadline;
- saves separate per-cycle recovery evidence and marks failed/interrupted runs accordingly, including failures with no metric samples.

The WPF recovery deadline starts after the independent Backend startup readiness gate. A run may therefore spend up to 120 seconds on Backend startup and another 120 seconds on WPF recovery. Waiting for the user's confirmation is intentionally not timed out.

Readiness export is disabled in ordinary launches. Only the audit helper supplies its owned temporary run directory and random run ID; these variables are cleared immediately after launch and consumed by WPF. The evidence contains no credentials, Discord IDs, messages, reaction payloads, or raw Backend generation. The Backend identity is represented by a segmented SHA-256 digest. The helper still launches no extra WPF instance per cycle and performs no automated Discord writes. Rendering, new-message delivery, selected Host visibility, write-back, duplicate notifications, and sound remain explicit user checkpoints; transport evidence is not claimed as visual proof.

New regression coverage includes independent missing signals, stale attempts, auth/terminal failures, Sales degradation, epoch changes, owned destination checks, a real readiness-file write, production coordinator hooks, and five refreshed sessions with unchanged credentials and recent20. An offline Windows PowerShell harness exercises 65 assertions, including the actual restart loop with mocked processes: a failed second cycle prevents the third from starting, and all five successful cycles require confirmation. It also checks stale/foreign/malformed reports, stable-interval resets, confirmation-time disconnects, empty metrics, and sanitized failure evidence. No live Discord session is started by these tests.

## Backend startup membership recovery corrective

The next user run confirmed baseline cycle 0 after 10.426 stable seconds, then failed cycle 1 with `PresenceBootstrapPending` followed by `RecoveryFailed`. The saved evidence records only one Backend restart, no repeated pairing confirmation, and zero Gateway disconnects. The helper correctly stopped before cycle 2; this run is not a five-cycle PASS.

The preserved Backend log at 02:22:52.959 KST showed two `NullReferenceException` failures in `DiscordNetChatSource.GetGuildAsync`, serving Chat catalog and Sales bootstrap requests while Discord was still initializing. Discord became Ready at 02:22:54.606. WPF subsequently received recent20 and complete Sales snapshots repeatedly, but never completed Presence bootstrap and exhausted its existing retry budget. The former warning log did not capture the HTTP status, so the original repeated Presence response code cannot be asserted directly from that log.

Code inspection and regression tests identified two startup defects:

1. Chat authorization dereferenced `rest.CurrentUser.Id` before the Discord REST identity existed. It had already started two REST operations before reaching that dereference.
2. `DiscordGuildMembershipVerifier` cached `VerificationUnavailable` for the same five-minute lifetime as a definitive membership decision. A transient startup, timeout, or upstream failure could therefore block the Presence bootstrap and WebSocket membership gates after Chat/Sales had recovered.

The correction checks for an initialized REST identity before issuing Chat or membership requests and returns temporary unavailability instead of throwing or declaring access revoked. Membership results are cached only when they are definitive `Member` or `NotMember`. Temporary failure still denies the current operation, but the next request can verify again immediately. The existing five-minute definitive lease, 128-entry bound, per-Guild/user keys, and NotFound/non-member denial remain unchanged. Caller cancellation is propagated and does not populate the cache; a late transient failure cannot overwrite a concurrently successful lookup. No authorization check is bypassed and no credential is deleted or replaced by this correction.

The WPF retry warning now includes a fixed recovery phase and numeric HTTP status, without request URLs, credentials, response bodies, or raw exception messages. Retry delays, retry limits, the 120-second audit deadline, ten-second stable gate, and user confirmation requirements are unchanged.

The first four offline regression cases reproduced the old behavior: the uninitialized Chat source threw the same null-reference exception, and three transient membership cases remained unavailable on the next request. All four passed after the correction. Expanded tests cover cold membership without external requests, timeout/503/403/429/network/internal-cancellation recovery, definitive positive/negative leases and expiry, NotFound, expired authorization, caller cancellation, concurrent lookup ordering, and bounded identity-separated caching.

An additional loopback integration test stops and recreates the Backend web host five times with the same credential state directory. Each host initially returns a synthetic temporary membership failure, then accepts a new Presence bootstrap and live WebSocket using the original credential without re-pairing or advancing a five-minute clock. A WPF coordinator regression verifies automatic recovery from a Presence 503 with recent20 and complete Sales, and checks that the new warning exposes only the safe phase/status. These are automated local tests with no real Discord connection or writes, not a substitute for the user's still-pending live five-cycle run.
