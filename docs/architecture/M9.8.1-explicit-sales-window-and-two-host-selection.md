# M9.8.1 explicit Sales window and two-host selection

## Product policy

LS Overlay tracks the newest 30 Sales posts. This is the complete authoritative
Sales domain for this product version, not a configurable history size, cache
optimization, or inference that older posts are missing.

The Session HUD has exactly two logical server-configured slots, `Host 1` and
`Host 2`. Each Windows client explicitly selects exactly one slot. There is no
Auto, Both, fallback, or automatic host-switching mode. Host 2 is used when Host
1 has closed their GTA session in the current server workflow, so inferring an
active host or presenting both is unnecessary and could show the wrong session.

M9.8.1 does not start M9.9 and does not retire Legacy UIA or Local RPC.

## Authoritative Sales window

`AuthoritativeSalesWindow.Size` is fixed at 30. A successful canonical rebuild
containing 0 through 30 messages, with one Complete completion observation for
every retained message, is Complete. Returning 30 messages is normal and does
not imply truncation. The implementation does not fetch message 31 merely to
prove completeness.

The Backend registry, Windows Remote cache, completion-observation set,
`SalesStateEngine` input, and UIA shadow target set are bounded to the same
newest-30 message IDs. A new post is ordered by `CreatedAt` and message ID; the
oldest out-of-window post and its observation are removed together.

Window eviction is an application-owned scope change, not a Discord delete.
`ApplyAuthoritativeWindowSnapshot` physically removes an evicted active record
without creating a Deleted tombstone or fabricating completion evidence. A real
Discord delete still uses the exact-delete path and retains the existing Deleted
tombstone semantics. It is followed by an isolated Sales resync so the next
older post can enter the authoritative window if required.

Partial/incomplete remains reserved for an actual defect within the window,
including a missing or non-Complete observation, sequence gap, generation
mismatch, failed canonical request, or authorization failure. Existing SOLD /
closed marker rules and trusted Complete-absence reopening rules are unchanged.

The Sales mutation journal remains separately bounded at its existing capacity;
it is not expanded to match or multiply the product window.

## Server host mapping

The canonical Backend-only configuration is:

- `LSO_SESSION_HOST_1_ID`
- `LSO_SESSION_HOST_2_ID`

Host 1 is required when explicit Session configuration is enabled. Host 2 may be
omitted during development; selecting an unconfigured Host 2 produces the
localized not-configured state without a crash. Values must be unique non-zero
Discord IDs. Malformed values, duplicate values, Host 2 without Host 1, and more
than two slots are rejected.

`LSO_TRACKED_HOST_IDS` remains a temporary developer-compatibility input only
when neither explicit variable is configured. It preserves list order as Host 1
then Host 2, rejects duplicates, and rejects more than two entries rather than
silently discarding them.

Actual host IDs are deployment data. They are not committed to C#, XAML,
protocol constants, tests, documentation, or public defaults. Startup logging
reports only the configured host count. The Backend converts IDs to stable
`HostSlot` values before transport; `HostPresenceSnapshot` contains slot, state,
occupancy, and observation time, but no host Discord ID.

## Per-client selection

Settings schema 15 persists `SelectedSessionHost` with exactly `Host1` and
`Host2`. New and migrated clients default to Host 1. Missing, invalid, or prior
experimental Auto/Both values normalize to Host 1 while unrelated extension
fields remain preserved.

The Settings ComboBox shows only localized Host 1 and Host 2 labels. Turning the
Session HUD off retains the selection but hides the presentation. When enabled,
the selected slot alone drives the HUD. An offline or unavailable selected host
never borrows the other slot's data.

The Remote transport may continue carrying the two small bounded slot snapshots.
The WPF client caches them and changes its local binding immediately when the
selection changes. Switching slots therefore requires no Backend restart,
Discord reconnect, re-pair, token refresh, or WPF restart. Different clients may
select different slots without changing the global Backend mapping.

## Validation and preserved boundaries

`tools/dev/run-ls-m98-local.ps1` prompts separately for Host 1 and Host 2. It
passes those values to the Backend process, then clears every Backend environment
variable before launching WPF. It preserves secure token input, loopback port
preflight, helper-owned cleanup, and refusal to terminate an unknown port owner.

M9.8.1 preserves Remote Sales-only resync, redundant `sales_ready` handling,
Forward custom-emoji rendering, Remote Chat, Sales status write-back, notification
sound baselining, UIA fallback, Local RPC, clean shutdown, existing Gateway
intents, and the existing minimal Bot permissions. General animated-media work,
Legacy retirement, deployment engineering, and M9.9 remain deferred.
