# M9.10 UIA Retirement and Remote-Only Sales Authority

Date: 2026-09-02  
Scope: remove Windows UI Automation from the current product architecture; do not redesign the product or publish a release

## 1. Result

M9.10 removes the Discord accessibility-tree scanner and every production Sales path that depended on it. Remote Sales canonical evidence from `LSOverlay.Backend` is now the only production authority allowed to change Sales completion state.

Historical M8/M9 documents remain unchanged as historical evidence. In particular, M9.9 accurately documents the architecture that existed before this retirement. This document supersedes those descriptions only for the current product architecture.

## 2. Current production path

```text
Discord Bot Gateway / REST
        ->
LSOverlay.Backend
        ->
Authenticated Remote Protocol
        ->
LSOverlay.RemoteClient
        ->
SalesPresentationCoordinator
        ->
SalesStateEngine
```

The Sales truth no longer depends on the Discord desktop window, accessibility tree, rendered reactions, window focus, selected Discord channel, or a polling worker.

The effective production Sales states are:

- `RemoteStarting`
- `RemotePrimary`
- `RemoteRecovering`
- `RemoteUnavailable`
- `AccessRevoked`

There is no UIA fallback or shadow comparison.

## 3. Local RPC policy

Local Discord RPC Main Chat is retained as a supported legacy Chat source and emergency compatibility path. Its message normalization can still carry generic shared data, but Local RPC is not an authoritative Sales completion provider.

Local RPC cannot independently prove the exact canonical absence of both completion reactions. M9.10 therefore never converts incomplete Local data into trusted `Complete` Sales evidence and never reopens a Sold item from Local absence.

When Main Chat uses Local RPC while Sales tracking is enabled, the authenticated Remote session still starts independently for Sales, Presence, and Sales write-back. A later milestone may consider retiring Local RPC Chat after a separately scoped compatibility and support review.

## 4. Domain semantics retained

- States remain `Pending`, `Sold`, and `Deleted`.
- Reaction ID `1451583544295034940` / name `SOLD` marks completion.
- Reaction ID `1418284521337651321` / name `closed` marks completion.
- Either marker is sufficient: `SOLD OR closed => Sold`.
- `NotObserved` is not interpreted as `NotSold`.
- `Sold -> Pending` is permitted only when trusted, complete, canonical Remote evidence shows both completion markers absent.
- The authoritative Sales window remains the newest 30 messages.
- Exact delete, eviction, Sales-only backfill/resynchronization, queue ordering, alerts, sound suppression, ownership, and bot-reaction semantics remain intact.

## 5. Failure and recovery

During a transient Remote interruption, the last trusted Sales state remains visible while health moves to recovering or unavailable. Write-back is disabled until a healthy `RemotePrimary` canonical state returns. Missing Remote evidence never fabricates a Sold-to-Pending transition.

Definitive `AccessRevoked` fails closed: presented Sales data is redacted, write-back stays disabled, and no legacy source is substituted. A later authorized canonical bootstrap may restore the presentation.

Remote replay and reconnect are generation/cursor guarded. A gap requests a Sales-only resynchronization; it does not merge uncertain mutations into trusted state.

## 6. Removed current-product dependencies

The current source no longer contains the application-owned accessibility adapter, Discord window locator, reaction-tree interpreter, UIA Sales observation provider, UIA-specific models, opaque-message UIA resolver, accessibility launch option, UIA health and fallback states, UIA metrics, UIA diagnostics, UIA settings, accessibility onboarding, channel-open remediation, or accessibility verification helper.

The WPF manifest value `uiAccess="false"` is the standard Windows execution-level declaration. It does not enable UI Automation and is not an LS Overlay scanner or accessibility dependency. Normal WPF control `AutomationProperties` metadata may remain for the application window's own accessibility; it is unrelated to observing Discord and provides no Sales evidence.

## 7. Settings migration

The settings schema moves from 15 to 16. Existing schema-15 files remain accepted. The retired `salesAcquisitionPreference` field is removed during migration, while unrelated unknown fields continue to be preserved. Existing atomic-save and backup-recovery behavior is unchanged.

## 8. Security and permissions

Remote authorization remains mandatory. Guild and authorized-channel checks, exact Author ID ownership, bot-owned reaction boundaries, server-side Bot token handling, DPAPI-separated Remote credentials, and `AccessRevoked` fail-closed behavior are unchanged.

No Bot permission or Gateway intent was added. Bot permissions remain View Channel, Read Message History, and Add Reactions. Gateway intents remain Guilds, GuildPresences, GuildMessages, GuildMessageReactions, GuildMessagePolls, and MessageContent; GuildMembers remains off.

## 9. Validation boundary

`LSO_REMOTE_ONLY_VALIDATION` remains useful as a Local-RPC-off audit mode. It no longer disables UIA because UIA does not exist in the current product architecture.

The M9.10 live helper validates normal Remote operation while Discord is minimized or showing an unrelated channel and performs a five-cycle Backend reconnect check. It owns and cleans up only the processes it starts, accepts the Bot token as a `SecureString`, keeps Host IDs Backend-only, checks port ownership before startup, and emits sanitized summaries.

## 10. Explicitly deferred work

M9.10 does not implement the fixed Minimal HUD direction, Session badge relocation, completed Sales-row removal UX, Sales text/mixed parser, fixed Main Chat channel allowlist, broader Settings redesign, branding changes, or LS Overlay visual overhaul. Those remain inputs to the later LS Overlay 2.0 UI/UX milestone.

The public rc.1 tag, release, artifact, and history remain immutable. M9.10 does not deploy the Backend, push commits, create a tag, or create a 2.0 release.

## 11. User-actual validation and resource evidence

The user ran both M9.10 helper modes on 2026-09-02. Quick Remote Sales validation completed after the user checkpoint, and the five-cycle reconnect validation completed with the WPF process kept open. The helper recorded five Backend restart cycles, zero Gateway disconnects, and zero slow-client disconnects. Helper-owned processes shut down cleanly after each capture.

The 66.157-second Quick sample recorded the following WPF values:

- CPU average: 0.167%
- Working Set: 275.868 MiB average, 281.754 MiB maximum
- Private Bytes: 189.741 MiB average, 198.082 MiB maximum
- Handles: 1,073.692 average, 1,084 maximum
- Threads: 26.846 average, 28 maximum

Compared with the M9.9 Remote-only WPF averages of approximately 267.063 MiB Working Set and 191.583 MiB Private Bytes, the M9.10 Quick average is about 8.805 MiB higher in Working Set and 1.842 MiB lower in Private Bytes. This short comparison is descriptive, not a regression verdict.

The 114.914-second reconnect sample recorded WPF Private Bytes of 255.440 MiB average and 278.445 MiB maximum. Its first-to-last-window trend was +43.588 MiB / +18.746%, classified `Possible Growth`. The earlier M9.9 reconnect signal was +23.892 MiB / +12.009%, so the growth signal remains and was larger in this run. UIA retirement must not be described as having solved a memory leak. The Backend reconnect trends were stable; a later long soak and release audit should investigate the retained WPF growth signal.

The user-actual functional checkpoint covered Remote Chat, canonical Remote Sales, the selected Host slot, duplicate suppression, operation with Discord on an unrelated channel or minimized, Sales/reaction updates without opening the Sales channel, own-message write-back after `RemotePrimary`, and the absence of retired sensor/channel-open warnings.
