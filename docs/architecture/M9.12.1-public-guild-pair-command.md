# M9.12.1 — Public Target Guild pairing command

## Scope

Allow ordinary Target Guild members to invoke `/lsoverlay pair code:...` without
Administrator, Manage Guild, another elevated permission, or an application role
allowlist. Preserve the Remote-only architecture and M9.12 lifetime fixes. No new
onboarding, UI, branding, intents, bot privileges, deployment or release.

## Exact baseline finding

`DiscordPairingCommand.Build()` previously did **not** set an elevated permission.
`HandleAsync(SocketSlashCommand)` contained no role/admin precondition; it passed
Discord's interaction Guild/user/bot identity to `PairingService.Approve`.

The verified defect was registration drift: `ReconcileAsync` fetched commands and
`HasExpectedShape` checked only type, pair/code option types and requiredness. An
existing command with restrictive default permissions but the right options was
accepted without updating its permissions. Shape changes deleted/recreated the
command. This audit did not fetch production command metadata or Integration
overrides, so it does not claim to know the server's previously registered bitset
or that an explicit Administrator check was removed from the product source.

## Discord.Net 3.20.1 semantics and correction

The Backend's pinned SDK version remains 3.20.1.

- `WithDefaultMemberPermissions(null)` produces an unspecified
  `Optional<GuildPermission>` in the builder.
- The guild-create REST helper converts that optional to a nullable API value,
  and the actual SDK serializer emits `"default_member_permissions": null`.
- Explicit numeric zero emits `"0"`, which Discord defines as disabled for
  ordinary members by default, not as unrestricted.
- The SDK read model collapses both API null and zero to `GuildPermissions(0)`.
  Comparing that read model cannot reliably distinguish the two policies.

The guild command definition now states the unrestricted default explicitly and
records Guild-only context. Reconciliation always calls the existing Target
Guild's CreateApplicationCommandAsync with that complete definition. Discord's
name/type-scoped POST is an upsert; no delete, global command, bulk overwrite, or
role/channel permission endpoint is called. Concurrent reconciliation still uses
the existing gate; failures mark pairing registration Degraded.

The Guild endpoint itself enforces the registration scope. Discord.Net's
guild-create implementation does not transmit global-only context settings;
Guild commands are not available in DMs regardless. The handler also rejects null
Guild/DM and unrelated Guild identity through the unchanged PairingService guard.

## Security preserved

Production still receives authenticated SocketSlashCommand events from the SDK;
the handler now accepts their existing ISlashCommandInteraction interface so the
same path can be exercised offline. There is no new HTTP approval endpoint and no
caller-supplied user/installation option.

Approval checks Target Guild, nonzero non-bot interaction user, code, expiry,
prior approver and consumption. Only the originating installation's independent
claim secret can claim its pending request; credentials remain user/Guild/
installation-bound and only hashes are persisted by the Backend.

Existing two-stage authorization is unchanged: trusted Guild interaction approves
the pairing; authoritative membership and channel access checks guard Remote data
and actions. Claiming a credential is not by itself authorization to read data.
Membership uncertainty still fails closed; existing membership lease expiry and
channel revocation semantics remain. Do not describe this as a new membership
REST lookup before the slash-command approval or credential claim.

Pairing results remain ephemeral; responses do not echo codes, claim secrets,
installation IDs or access tokens. Invalid calls do not create pending pairings.
Existing bounds: 64 pending pairings, two-minute expiry, 128 credentials, 5/minute
pairing creation and 60/minute claim HTTP request limits (no queue).

Bot permission ceiling stays View Channel / Read Message History / Add Reactions.
Intents remain Guilds, GuildPresences, GuildMessages, GuildMessageReactions,
GuildMessagePolls and MessageContent. GuildMembers stays off.

Remaining production Administrator/management mentions are the Discord channel
permission evaluator (Discord permission semantics) and excess-bot-privilege
audit/logging. None is a precondition for pairing.

## Server permissions

The application default is ordinary-member access, subject to Discord's ordinary
Use Application Commands permission and explicit server Integration/channel
overrides. This update does not bypass, remove or rewrite those overrides. No
Developer Portal manual toggle is needed to reproduce the application default.
If access remains unavailable after registration, inspect the app's live command
and server overrides; do not add a privileged role whitelist as a workaround.

## Verification and user check

Baseline: 1,200 tests. New focused command tests cover the actual builder, the
installed SDK's serialized REST payload, repeated upsert from restricted defaults,
Guild isolation, registration failure/concurrency, ordinary-user identity, invalid
and expired codes, private replies, claim secret, bots and DM/wrong-Guild rejection.
The in-memory REST transport allows only synthetic Guild POSTs and never opens a
network connection. Additional loopback tests exercise authoritative membership
rejection and revocation after the existing lease expires.

The additional membership tests exposed an existing
HTTP error: Results.Forbid() is used without an ASP.NET authentication handler,
so a non-member bootstrap returns 500 rather than 403. Access is denied, but the
response is incorrect. The user explicitly approved a narrow response-only fix.

Sales bootstrap) now return HTTP 403 directly. Their conditions and authorization
decisions are unchanged; no ASP.NET authentication scheme or new privileges were
introduced. Loopback regressions verify all four branches and membership expiry.
