# M9.9 Final Consolidation and LS Overlay 2.0 Readiness

Date: 2026-09-02  
Scope: engineering audit only; no feature expansion, Legacy removal, deployment, rename, packaging, tag, or release  
Final verdict: **READY WITH BLOCKERS** — Quick, corrected Remote-only, and Reconnect are accepted; the 30-minute Soak is explicitly waived and representative Linux resource evidence remains pending

## 1. Executive result

M9.9 adds an evidence boundary for developer-only Remote-only validation, an isolated performance/soak/reconnect audit helper, machine-readable dependency and capacity inventories, and regression gates. It does not remove or silently weaken Local RPC, OAuth, UI Automation (UIA), accessibility remediation, or any rc.1 asset.

Quick, corrected Remote-only, and five-cycle reconnect user-actual runs are accepted. The user explicitly deferred the 30-minute soak because of the available validation time; it is recorded as `NOT RUN / WAIVED`, never as a pass. Long-duration resource stability and representative Linux hosting measurements therefore remain P2 release-readiness risks rather than known product correctness failures.

## 2. Preserved product policy

- Remote Chat and Remote Sales are the normal primary sources when the user selects Remote.
- Sales uses the newest 30-message authoritative window.
- The Backend accepts at most two configured session hosts. WPF receives only `HostSlot` 1 or 2, never a configured host ID.
- The user explicitly selects Host 1 or Host 2. There is no Auto, Both, or silent fallback host selection.
- Remote write-back remains available only when Remote Sales is canonical and `RemotePrimary`.
- Authorization denial is absolute and cannot be bypassed through UIA.
- Human-created reactions remain human-owned. Bot-created state remains independently reversible through the overlay.
- The rc.1 public release, tag, artifact, manifest, and public history remain unchanged.

## 6. UIA and Local RPC retirement readiness

Remote paths are sufficiently separated to measure independence, but not yet sufficiently evidenced to delete fallback code. Local RPC and UIA should be demoted in product messaging after the live M9.9 evidence passes, while remaining available behind explicit Legacy/rollback selection for the 2.0 RC.

Removing either path now would raise recovery risk for Backend outage, pairing trouble, channel authorization changes, and rare Remote normalization differences. The recommended retirement sequence is:

1. Ship 2.0 RC with Remote primary and existing fallbacks intact.
2. Collect sanitized Remote-only/reconnect/soak results and support incidence.
3. Measure actual fallback activation and failure categories.
4. Deprecate fallback UI only in a later milestone with an import/recovery plan.
5. Remove Local RPC, OAuth, UIA, and accessibility remediation together only after an explicit release decision.

## 7. Performance baseline method

The new helper samples both helper-owned WPF and Backend processes every five seconds by default. It records normalized CPU, Working Set, Private Bytes, handles, threads, and—on Windows—GDI and USER objects. It computes average/minimum/maximum, CPU p95, and first-20% versus last-20% memory trends.

Required comparison phases are:

1. cold startup and pairing/readiness;
2. connected idle;
3. active Chat/Sales/Presence;
4. media-heavy messages where practical;
5. Backend restart and recovery;
6. Remote-only operation.

External low-overhead sampling cannot continuously read the WPF managed heap. This is reported as unavailable rather than guessed. Process Private Bytes plus handles/threads/GDI/USER trends are the primary native/retention signals, supplemented by the existing in-app diagnostic snapshot and bounded cache metrics.

## 9. Memory and bounded-state audit

The authoritative list is [m99-runtime-bounds.json](m99-runtime-bounds.json). Important limits include:

- Main Chat: 20 messages.
- Authoritative Sales: 30 messages; tombstones: 256.
- Chat streams: 16 active channels, 20 bootstrap messages, 128 journal events per channel, 256 outbound events per subscriber.
- Sales stream: 256 journal and 256 outbound events.
- Publication and Backend journals: 2,048 events; publication outbound: 256.
- Remote client staged events: 256 for Chat and 256 for Sales.
- Pairings: 64; credentials/authorization leases: 128; canonical authors: 512.
- Remote connections: 64 global and 2 per installation.
- Sales write-back: 256 dedupe entries, 256 versions, 8 requests/minute/client window.
- Media caches: 64 emoji, 24 thumbnail, 24 sticker bitmaps; 12 MiB maximum per download.
- UIA scan cache: 8,000 nodes per scan.
- Inbound WebSocket control message: 16 KiB.

All audited long-lived collections have a finite capacity, eviction rule, lifetime owner, or both. The live soak remains necessary to find retained WPF visual/bitmap/native resources that a static bound cannot prove.

## 10. Media memory and bandwidth

M9.9 adds no animated-media support. WPF downloads Discord media directly from HTTPS metadata URLs, validates scheme/host expectations in the existing media path, caps each response at 12 MiB, decodes to bounded display dimensions, freezes the bitmap, and stores it in a bounded cache.

The Backend normalizes and transmits message text plus metadata/URLs. It does not download or proxy media bytes. Therefore steady-state Backend bandwidth is driven by Discord Gateway traffic, bounded REST bootstraps, JSON protocol events, heartbeats, and write-back requests—not attachment payload transfer. Exact bytes/hour depend on channel traffic and must be measured in the deployment environment.

## 11. Soak tooling and trend model

`tools/dev/run-ls-m99-audit.ps1 -Mode Soak` defaults to 30 minutes and a five-second interval. Samples are retained in a bounded accumulator (maximum 21,600), then written as sanitized JSON and CSV.

Trend classification compares the first and last 20%:

- `Stable`: growth below both the moderate absolute/relative threshold.
- `Possible Growth`: at least 16 MiB and 10% increase.
- `Needs Investigation`: at least 64 MiB and 25% increase.
- `Unavailable`: no finite samples.

Thresholds are triage signals, not proof of a leak. A rising handle/thread/GDI/USER trend, repeated reconnect increase, or continued post-activity memory climb also requires investigation even if byte thresholds are not crossed.

Status: automated synthetic bound/trend/sanitizer tests pass; the user explicitly waived the 30-minute run because of the available validation time.

## 15. Protocol, settings, and startup audit

Protocol v1 remains transport-neutral. It covers pairing, bootstrap, Chat catalog/bootstrap/mutations, Sales bootstrap/mutations/evidence/status action, Presence, resume/resync, heartbeat, and event envelopes. The Protocol assembly has no Discord.Net reference; JSON serialization emits no CLR `$type` metadata. WebSocket inbound control messages are limited to 16 KiB and binary messages are rejected.

Settings schema remains 15 because Remote-only is an environment-scoped audit mode, not persisted product state. Existing migration, unknown-field preservation, source selection, Remote endpoint/channel, Host 1/2 selection, Sales behavior, and audio settings remain. Remote access credentials remain in a separate DPAPI-protected file rather than settings JSON.

WPF startup initiates Sales, Presence, and channel catalog work independently; initial Chat can render without waiting for Sales or Presence. Backend startup avoids full member fetch, full reaction-user fetch, all-channel normalization, and media hydration. Chat bootstrap fetches only the selected channel's bounded recent messages; Sales fetches the fixed authoritative window.

## 20. Memory optimization recommendations

Ranked by expected value and risk:

1. **Measure first:** accept a real 30-minute Remote-only/media-heavy trend before changing cache sizes.
2. **High value / low risk:** retain frozen/downscaled bitmaps and bounded caches; verify cache clearing releases native image resources after media bursts.
3. **High value / low risk:** keep UI update coalescing and the 20/30 presentation windows; avoid materializing duplicate message projections.
4. **Medium value / low risk:** add an optional internal EventPipe/GC counter collector in a later diagnostics milestone if Private Bytes trends need attribution.
5. **Medium value / medium risk:** tune emoji/thumbnail/sticker capacities only from observed hit rate and decoded-byte metrics.
6. **Low immediate value / high risk:** do not remove UIA/Local RPC merely to reduce idle memory before rollback evidence is accepted.
