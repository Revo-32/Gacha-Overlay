# M8.1 Onboarding / Server Settings / Recovery UX 완료 보고

최종 갱신: 2026-09-01 · Onboarding Sales compatibility 안내창 수정 및 사용자 재검증 반영

## 1. 요약

M8.1의 First-run Onboarding, 고정 Production Server 설정, 단일 Main 채널 선택, 트랜잭션 Main 전환, Windows 자동 시작, Discord 자동 실행, 접근성 안내 및 복구 UX를 구현했다. Settings는 `General → Discord → Server → HUD → Chat → Media → Sales → Hotkeys → Diagnostics → Developer`의 정확히 10개 카테고리다.

Production Guild와 Sales 채널은 하나의 고정 profile을 사용하고, 사용자는 Server 화면에서 지원되는 text channel 하나만 Main으로 선택한다. Server 전체 구독은 추가하지 않았으며 M7.5/M8.0의 HUD, Sales queue, media, forward/opaque, theme, typography 및 crash-safe 저장 구조를 유지했다.

최초 M8.1 사용자 검증 중 Discord가 실행된 상태에서 Onboarding의 Sales compatibility action을 누르면 앱이 종료되는 문제가 확인됐다. 로그에서 숨겨진 Settings 창 때문에 WPF 안내창 owner가 `null`이 된 것이 원인임을 확인했다. Onboarding 창 우선 owner와 ownerless fallback을 적용한 뒤 전체 자동 검증을 다시 통과했으며, 동일 절차의 사용자 재검증에서도 정상 동작이 확인됐다.

## 2. First-run Onboarding

Onboarding은 다음 6단계다.

1. Language
2. Discord credential/authentication
3. Fixed Production Server 확인
4. Main Channel 선택
5. Sales accessibility 확인 또는 Sales Tracking OFF 선택
6. HUD F9/F10 및 drag/click-through 안내

새 설치 기본 언어는 English다. EN/KO/JA를 즉시 변경할 수 있고, 별도 설정 또는 credential 계층을 만들지 않고 기존 `FoundationViewModel`, `ISettingsStore`, DPAPI credential/auth service를 그대로 재사용한다.

완료 시 `OnboardingVersion = 1`을 저장한다. 창을 중간에 닫아도 앱과 tray는 유지되며, 다음 실행에는 실제 미완료 상태를 검사해 재개한다. Client ID만 있고 보호된 Client Secret이 없으면 Discord 단계로 돌아가며, 유효한 Main이 없으면 Server 단계부터 재개한다. General의 `Initial Setup 다시 실행`은 현재 설정과 credential을 삭제하지 않고 처음부터 다시 확인한다. 동시에 두 개의 Onboarding 창은 만들지 않는다.

## 3. Server Settings

Discord 다음에 Server 카테고리를 추가했다. Guild는 `ProductionServerProfile.GuildId`, Sales는 `ProductionServerProfile.SalesChannelId`로 고정되며 selector나 numeric ID 편집 UI를 제공하지 않는다.

인증된 임시 RPC session에서 `GET_GUILDS`로 고정 Guild만 확인하고, 그 Guild에 대해서만 `GET_CHANNELS`를 호출한다. Main selector에는 type 0 text channel만 friendly `#채널명`으로 표시하며 voice/category/stage/forum 등은 제외한다. 고정 Sales 채널도 Main 후보에서 제외한다. Sales friendly name을 찾지 못해도 다른 채널을 임의 선택하지 않는다.

Server 화면을 열 때 lazy load하고, 5분 session cache와 single-flight를 사용한다. 수동 Refresh는 cache를 우회한다. RPC generation이 바뀌면 cache를 무효화하고 이전 generation에서 늦게 완료된 결과는 stale로 폐기한다. 마지막 Server 카테고리와 scroll 위치도 기존 Settings persistence로 저장한다.

## 4. Main Channel Transactional Switch

Main 변경은 다음 순서로 처리한다.

1. 고정 Guild의 최신 `GET_CHANNELS` 결과에서 후보를 다시 검증한다.
2. 새 Main의 `MESSAGE_CREATE/UPDATE/DELETE` 세 이벤트를 먼저 구독한다.
3. 새 Main `GET_CHANNEL` snapshot을 bootstrap한다.
4. RPC client, connection generation, 기존 target, switch revision이 여전히 유효한지 확인한다.
5. 같은 generation에서 Main store만 최근 20개로 원자 교체한다.
6. Sales store와 Sales queue는 그대로 유지한다.
7. 새 Main을 publish한 뒤 기존 Main의 세 이벤트 구독을 해제한다.

동일 채널은 no-op이다. 검증·구독·bootstrap 중 실패하면 기존 Main과 persisted Main을 유지하고 준비한 새 구독을 정리한다. 성공 후에만 `DiscordMainChannelId`를 crash-safe settings에 저장한다. 저장 실패 시 기존 Main으로 보상 전환을 시도하고 persistence failure를 사용자 상태로 반환한다.

단조 증가 switch revision, active client/session/generation guard로 늦은 B 결과가 최신 C 선택을 commit하지 못한다. Server selector 자체에도 독립적인 selection revision을 적용해 늦은 B UI 결과가 C 표시를 되돌리지 못한다. 전환 시 이전 Main의 Forward/Opaque lookup을 취소하고 registration stamp와 현재 store membership을 재검증하므로 늦은 비동기 결과가 새 Main에 섞이지 않는다.

## 5. Startup

Windows Auto-start는 기본 OFF다. 사용자가 켜면 관리자 권한이 필요 없는 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`에 현재 실행 파일을 등록한다.

경로는 개발 폴더나 버전별 설치 경로를 hard-code하지 않고 `Environment.ProcessPath`에서 가져와 따옴표로 감싼다. portable 실행 파일을 옮긴 뒤 새 경로에서 앱이 시작되면 현재 path로 registration을 self-heal한다. 등록 또는 복구가 실패해도 앱은 계속 실행되고 설정은 OFF로 되돌아간다.

## 6. Discord Launch / Accessibility

Discord Auto-launch는 기본 OFF다. ON이어도 먼저 Discord/Canary/PTB/Development process를 확인하며 이미 실행 중이면 새 instance를 시작하지 않는다. 미실행 상태에서는 registered `discord://-/` protocol을 사용해 앱 startup당 최대 한 번만 실행을 시도한다. 실패 시 tight retry 없이 `Discord를 직접 실행한 뒤 다시 연결하세요` 상태와 기존 Reconnect action을 제공한다.

일반 Auto-launch와 Sales accessibility launch는 분리했다. 사용자가 접근성 실행을 명시적으로 요청하고 Discord가 꺼져 있을 때만 `%LOCALAPPDATA%\Discord\Update.exe --processStart Discord.exe --process-start-args "--force-renderer-accessibility"`를 사용한다. Discord가 이미 실행 중이면 자동 종료하거나 재시작하지 않고 사용자가 직접 종료 후 다시 실행하도록 안내한다. production source에는 `Process.Kill` 경로가 없다.

접근성 안내창은 Onboarding 실행 중에는 Onboarding 창을 owner로 사용하고, owner 창이 전혀 없는 lifecycle에서도 ownerless WPF overload로 안전하게 표시한다. 숨겨진 Settings 창 때문에 null owner가 전달되어 앱이 종료되는 경로를 제거했다.

Sales UIA unavailable은 Main RPC 연결을 Error로 바꾸거나 trusted Sales queue를 초기화하지 않는다. Sales Tracking ON이면 Onboarding에서 안내하고 진행을 멈추며, 사용자가 Sales Tracking을 OFF로 선택하면 기존 Main 설정을 유지한 채 계속할 수 있다.

## 7. Recovery UX

Discord 화면은 RPC connection, OAuth/auth, process-related connection state와 Sales accessibility를 사용자 문자열로 표시한다. 기존 auto reconnect/backoff와 manual reconnect signal을 재사용하므로 별도 reconnect engine이나 중복 reconnect operation을 만들지 않는다.

`다시 인증`은 기존 authentication service의 저장 OAuth session만 지우고 Client ID/Client Secret 전체 삭제와 구분한다. Server Refresh는 고정 Guild/channel discovery만 다시 실행한다. Guild 누락 또는 channel lookup 실패는 credential이나 기존 Main 설정을 삭제하지 않는다. 기술적인 exception 원문이나 raw RPC payload/secret은 사용자 UI 및 로그에 노출하지 않는다.

## 8. Migration / Persistence

Settings schema는 10에서 11로 정확히 한 단계 증가했다. 신규 persisted field는 `OnboardingVersion`, `WindowsAutoStart`, `DiscordAutoLaunch`다.

schema 10 migration은 기존의 유효한 MainChannelId, Discord Client ID/redirect, 언어, HUD/Chat/Media/Sales/Hotkey/Theme 설정과 알 수 없는 extension field를 보존한다. legacy Guild/Sales 값은 고정 Production profile로 교체하며, 현재 schema 파일이 수동 변형된 경우에도 load 시 디스크까지 self-heal한다. migration은 idempotent다.

Client Secret과 OAuth token은 기존 DPAPI 파일에 별도로 보존되므로 settings migration이나 Server discovery failure가 credential을 지우지 않는다. 모든 Settings save는 기존 unique temp file, disk flush, deserialize validation, atomic replace 및 `.bak` 복구 구조를 계속 사용한다.
