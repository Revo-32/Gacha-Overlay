# M9.6 Remote Sales Cutover

> Current policy note: M9.8.1 replaces the earlier presentation-cache bounds
> with one fixed authoritative newest-30 Sales window across messages,
> observations, engine input, and UIA targets.

## Decision

Official Remote Discord Sales evidence is the preferred production source after a
canonical Sales bootstrap is committed and the current subscription reports Ready.
The existing `SalesStateEngine` remains the only domain engine.

`SalesAcquisitionPolicy` owns the source decision:

- `LegacyOnly`: Local RPC messages plus UIA completion evidence.
- `RemoteStarting`: Remote was explicitly selected but has no trusted canonical
  bootstrap yet. Existing trusted domain state is retained.
- `RemotePrimary`: the current Remote generation has Complete message/evidence
  coverage. Remote message and completion evidence is authoritative.
- `RemoteRecovering`: reconnect, resync, or temporary authorization verification
  failure. The trusted queue is retained and UIA remains shadow-only.
- `UiaFallback`: an explicit terminal Remote failure, missing credential, unavailable
  channel, or Developer Force Legacy override. UIA may drive completion evidence.
- `Unavailable`: confirmed `AccessRevoked`. No Remote, Local RPC, or UIA production
  evidence is accepted until authorization is restored.

Provider handoff is policy state, not domain evidence. A handoff by itself never calls
the domain engine and cannot create a queue transition or Personal Alert.

## Promotion and generation safety

Remote promotion requires all of the following:

1. Sales tracking is enabled and Main Chat Source is Remote.
2. The Remote client reaches Sales Ready.
3. The bootstrap protocol and generation are valid.
4. Bootstrap coverage is `Complete`.
5. Every canonical message has exactly one Complete completion observation.

`Complete` is scoped to the Backend's bounded authoritative Sales retention domain:
the latest 100 messages retained by `ActiveSalesStreamRegistry`. A response containing
exactly 100 messages is therefore Complete for the product domain; message count alone
cannot prove that the retained window is truncated. `Truncated` remains reserved for a
future source that positively reports missing data inside that authoritative window.

The coordinator retains the accepted Remote generation and latest sequence. A
mutation from another generation or a non-next sequence is ignored. Reconnect,
resync, rollback-to-Auto, and authorization uncertainty invalidate the accepted
generation. A fresh canonical bootstrap is required for re-promotion.

## UIA shadow and fallback

UIA keeps its existing approximately 1000 ms cadence. M9.6 deliberately does not add
a polling optimization or a correctness timer. While Remote is Primary, Starting, or
Recovering, UIA batches are used only for bounded low-cardinality comparison metrics;
they are not submitted to `SalesStateEngine` and cannot cause remediation UI.

When UIA is the effective fallback, the existing channel-open remediation remains
active. A terminal fallback retains the last trusted Remote message set and merges
Local RPC messages by exact MessageId, preventing an incomplete Local snapshot from
emptying the queue. A message previously observed by Local RPC and then removed in a
same-generation ready state remains an exact, idempotent delete.

## Authorization boundary

`AccessRevoked` is a confirmed denial and has absolute precedence over Developer
rollback. It selects `Unavailable`, blocks UIA and Local production evidence, and
preserves but does not extend trusted state. `AuthorizationUnavailable` is a temporary
verification failure; it selects `RemoteRecovering`, preserves trusted state, and uses
the existing bounded reconnect schedule. Exhausted terminal recovery may select
`UiaFallback`, but confirmed denial never does.

The Discord protocol remains read-only. M9.6 adds no mutation endpoint, no reaction
write, no new Gateway client, no new credential, no member intent, and no new Bot
permission.

## Developer rollback

Developer settings expose persisted `Sales Evidence Mode` values:

- `Auto` (default): canonical Remote preferred.
- `Force Legacy/UIA`: Remote transport may remain available for diagnostics, but
  Remote evidence cannot drive production state.

Returning from Force Legacy to Auto restarts the Remote session and requires a fresh
canonical bootstrap before promotion.

## Diagnostics and bounds

Diagnostics show effective source, Remote phase, UIA state (including Shadow), and
merged Sales health. Local metrics count source transitions, promotion failures,
agreement/conflict and availability categories without MessageId labels or message
content. Remote presentation message/evidence caches are each capped at 256 entries,
and the Remote client keeps its existing bounded staged-event journal.

## M9.6 corrective bootstrap latency

The Main Chat REST bootstrap is committed to application ingress as soon as it is
available. It does not wait for Remote Sales bootstrap or member-name enrichment in
the Sales channel. The combined stream still starts from both captured generations,
so Gateway mutations that race with either REST snapshot are replayed without a gap.

Backend bootstrap normalization preserves per-author ordering while processing up to
four different authors concurrently. The canonical author resolver also uses an
already-observed target-Guild socket member before issuing a targeted REST lookup.
This keeps the M9.3.1 nickname policy while avoiding a serial REST waterfall and
duplicate same-author lookups during a large Sales bootstrap.
