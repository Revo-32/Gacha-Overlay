## Per-user channel authorization

`GET /api/v1/chat/channels` returns only target-Guild text and announcement channels
that both the authenticated Discord user and the Bot can read. Bot visibility is
never treated as user authorization.

The evaluator follows Discord's documented order exactly:

1. `@everyone` Guild permissions;
2. all member role permissions combined with OR;
3. Administrator bypass;
4. `@everyone` overwrite deny, then allow;
5. all applicable role overwrite denies combined, then all allows combined;
6. member overwrite deny, then allow.

Both `ViewChannel` and `ReadMessageHistory` are required. Role position and hierarchy
are not permission shortcuts. The implementation uses targeted REST lookup for the
single authenticated member and the Bot member, Guild roles, and channel overwrites.
It never invokes `DownloadUsersAsync`, keeps `AlwaysDownloadUsers` false, and leaves
the `GuildMembers` Intent off.

Authorization is a bounded, per-user, approximately two-minute lease with
single-flight refresh. An expired lease never serves stale content. A removed member
or lost channel permission becomes `chat_access_revoked`; a temporary Discord REST
failure becomes `chat_authorization_unavailable` and suspends content. Channel,
role, and targeted member updates invalidate cached decisions.

Reference: <https://docs.discord.com/developers/topics/permissions>

## HTTP catalog and race-safe bootstrap

- `GET /api/v1/chat/channels` returns the authorized catalog.
- `POST /api/v1/chat/bootstrap` accepts protocol version and channel ID.
- Bootstrap returns the channel descriptor, a channel-specific generation, the
  latest channel sequence, and at most the most recent 20 messages.

The Backend activates the channel stream before issuing the Discord REST recent
message request. Gateway create/update/delete mutations arriving during that request
enter the channel journal. Under one synchronization boundary, the REST snapshot is
installed and all mutations after the captured start sequence are replayed. If that
window fell out of the bounded journal, bootstrap fails closed and requires resync.
This prevents the REST-to-Gateway gap without holding locks during network I/O.

Updates replace canonical content but preserve the original creation time and
therefore do not reorder history. Deletions remove the item. Ordering is creation
time then Discord snowflake ID.

## Bounded active streams

The Backend keeps no unbounded Guild-wide message mirror:

- maximum active chat channels: 16;
- channel mutation journal: 128 entries, oldest first eviction;
- per-client chat outbound queue: 256 entries;
- retained recent state per active channel: 20 messages;
- idle channel eviction: 10 minutes when it has no subscriber;
- canonical update coalescer: at most 256 message keys;
- update debounce/single-flight window: 100 ms per channel/message.

Deep message normalization and canonical update REST fetches occur only for active
channels. Inactive poll votes and message updates cause no REST message lookup.

## Complete message transport

Protocol V1 remains additive and transport-neutral. `ChatMessage` carries:

- message ID/type/raw type/flags, channel and Guild IDs, timestamps, pin/TTS state;
- author ID, username, global/display name, exact Guild nickname, Bot/webhook flags;
- text and parsed custom emoji metadata;
- attachment URLs, proxy URLs, dimensions, content type, description/title, size,
  ephemeral state, and voice duration/waveform metadata;
- complete embed description, fields, author/footer/provider, media, color, and time;
- user/role/channel mentions;
- stickers and CDN asset metadata;
- reply reference and resolved message where available;
- immutable forwarded snapshots, deliberately without an invented source author;
- legacy and Components V2 structures, including nested containers/sections, text,
  media gallery, file, thumbnail, separator, button/select data;
- polls, answers, counts, self-vote state, expiry, layout, and finalization;
- raw type and bounded unknown component payload for future SDK-supported forms.

Discord documents that forwarded snapshots exclude `author`, that snapshots are
immutable, and that voice message duration/waveform live on the attachment. The
normalizer preserves those semantics rather than guessing an author or downloading
media through the Backend.

Reference: <https://docs.discord.com/developers/resources/message>

## Gateway and canonical updates

Discord.Net remains pinned to 3.20.1 and Backend-only. The exact Gateway Intents are:

- Guilds;
- GuildPresences;
- GuildMessages;
- GuildMessageReactions;
- MessageContent;
- GuildMessagePolls.

`GuildMembers` remains off. The 3.20.1 surface was inspected before enabling
`GuildMessagePolls`; its `PollVoteAdded` and `PollVoteRemoved` events provide the
message/channel identity required for targeted refresh.

`MESSAGE_CREATE` is normalized directly for an active channel. `MESSAGE_UPDATE` is
partial by Discord contract, so it never patches from the Gateway object: the
per-message coalescer performs a canonical REST `GetMessageAsync`. NotFound becomes
delete; a temporary failure emits controlled `chat_resync_required`. Poll vote events
use the same canonical path. Delete and bulk delete publish channel-specific deletes.

## WebSocket controls and authorization lease

The existing `ls-overlay.v1` WebSocket adds explicit frames:

- client: `chat_subscribe`;
- server: `chat_ready`, `chat_failed`, `chat_resync_required`;
- data: `chat_message_create`, `chat_message_update`, `chat_message_delete`;
- access: `chat_access_revoked`, `chat_authorization_unavailable`,
  `chat_channel_unavailable`.

Presence resume/replay/live and heartbeat behavior is unchanged. Chat has its own
channel generation and sequence. A subscription replays through a cutoff while the
post-cutoff queue is already registered, then becomes live. Slow clients are isolated
by bounded queues.

The connection refreshes authorization before the two-minute lease expires. During a
temporary verification outage delivery is suspended, never served from an expired
decision. If mutations were missed, recovery explicitly requires resync. Revocation
disposes the subscription.

## Transactional RemoteClient channel switching

`LSOverlay.RemoteClient` exposes catalog/bootstrap APIs and `StreamChatAsync`. Every
channel request has a monotonically increasing switch generation. The old committed
channel remains active while the replacement is authorized, replayed, and staged.
Only `chat_ready` for the latest requested switch commits the replacement. Replay
received before ready is bounded and staged. Therefore a slow request for channel C
cannot overwrite a later request for channel D.

The client validates channel ID, channel generation, switch generation, and strictly
contiguous channel sequence before raising a normalized mutation. Authentication,
resync, channel unavailable, and access-revoked states remain distinct.

## Core ingress adapter and WPF isolation

`RemoteChatIngressAdapter` is a non-production bridge from `ChatBootstrapResponse`
and `ChatMutationEnvelope` into `IOverlayMessageIngress`. It maps the complete rich
metadata into transport-neutral Core records and uses `ReplaceMain` for a committed
channel switch. Its comment and project boundary explicitly state that it is for
probe/tests only.

`GachaOverlay.App` does not reference `LSOverlay.RemoteClient`, does not construct the
adapter, and contains no remote endpoint startup. This prevents an accidental provider
cutover before live acceptance.

## Chat Probe and one-command helper

From the repository root:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\tools\dev\run-ls-m93-local.ps1"
```

The helper prompts securely for the Bot Token, launches Backend in a hidden process,
clears the token from the parent before starting the Probe, and cleans every temporary
environment value/state file/process in `finally`. The Probe performs pairing,
authenticated Presence bootstrap, authorized channel catalog, NUMBER-based channel
selection, recent-20 bootstrap, chat subscribe, channel switching, and compact
feature-coverage summaries. It never prints access, pairing-claim, or Bot secrets.

## Automated verification boundary

Automated network tests use loopback Kestrel and synthetic services only; they do not
contact Discord. Unit/integration coverage includes the permission algorithm,
user-and-Bot access, lease cache/single-flight/fail-closed behavior, bootstrap race,
20-message retention, ordering, delete, replay, journal and active-channel bounds,
idle eviction, update coalescing, Intent boundary, rich protocol round-trip, Core
adapter mapping, end-to-end catalog/bootstrap/subscription/mutation, and rapid C-to-D
transactional switching.

Real Discord validation is a separate user acceptance step and must not be reported
as passed until the M9.3 helper is actually run.
