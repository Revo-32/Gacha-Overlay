# M9.3.1 author consistency and Forward validation

M9.3.1 is a corrective patch only. It does not activate the WPF remote client,
change Sales, expand Gateway intents or Bot permissions, or start M9.4.

## Root cause

Discord.Net 3.20.1 constructs a Guild `MESSAGE_CREATE` author from the socket
Guild cache. It applies the event's member payload when the author is absent,
but an already cached user can therefore remain user-only. Its REST
`GetMessageAsync` and `GetMessagesAsync` paths also look up the author in the
Guild cache and otherwise create a global `RestUser`. The type and freshness of
the SDK author object can consequently differ between Gateway CREATE and the
canonical REST UPDATE fetch even though the Discord AuthorId is identical.

The former mapper selected `IGuildUser.DisplayName` when the SDK object was
Guild-aware and otherwise selected global display name. That made source-path
object shape decide between values such as `ItoToko` and `REVO*32`.

## Canonical author policy

Every remote Bootstrap, CREATE, UPDATE, and resolved Reply author now passes
through the Backend-owned `CanonicalRemoteAuthorResolver` in this order:

1. exact Guild nickname present on the current Discord.Net author object;
2. verified target-Guild nickname from bounded targeted member resolution;
3. global display name;
4. username;
5. `Unknown` only when no real value exists.

Current-message Guild data refreshes and outranks cached data. Exact data does
not cause a REST member request. The targeted cache is limited to 512
Guild/Author pairs with a 15-minute TTL, includes a bounded negative result,
and uses a 30-second backoff after temporary member-resolution failures. It
never downloads or retains a whole Guild member list. GuildMembers Intent
and `AlwaysDownloadUsers` remain disabled. A Guild member update invalidates the
affected author cache entry so a real nickname change can be observed.

`ChatAuthor.UserId` remains the immutable identity. DisplayName and
GuildNickname are presentation fields only.

## Forward Probe output

The local Transport Probe retains the one-line wrapper summary and, when a
message has forwarded snapshots, prints bounded details for up to four
snapshots and four attachments per snapshot. It shows up to 240 characters of
snapshot text plus safe file name, content type, size, and dimensions. URLs,
proxy URLs, waveform data, raw JSON, tokens, claim secrets, and authorization
headers are not printed.

Forward snapshots remain immutable Discord `MessageSnapshot` data. Original
author identity is not available in that contract and is printed explicitly as
`originalAuthor=<unavailable>`; it is never inferred from the forwarding user
or fetched from the source message.

## Remaining user validation

Run the existing helper without changing the machine-wide PowerShell policy:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\tools\dev\run-ls-m93-local.ps1"
```

Only these checks remain after the corrective build:

1. send and edit one ordinary message; CREATE and UPDATE must show the same
   author for the same MessageId;
2. forward a text message into the selected Main channel; the Probe must show
   `forwards=1` and the actual Forward snapshot text;
3. forward an image/attachment message; the Probe must show `forwards=1`,
   `Forward[1]` attachment count, and safe media metadata.

No other M9.3 live test needs to be repeated.
