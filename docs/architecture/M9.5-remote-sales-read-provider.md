# M9.5 Remote Sales Read Provider

> Current policy note: M9.8.1 supersedes the original transport-retention size.
> The newest 30 Sales posts are now the complete authoritative product window;
> see `M9.8.1-explicit-sales-window-and-two-host-selection.md`.

## Scope

M9.5 adds an opt-in, read-only Remote Sales path to the existing LS Overlay Bot Gateway,
authenticated transport, and WPF client. It does not remove Local RPC Sales or the UIA
completion observer, does not write to Discord, and does not perform a mandatory production
cutover.

Remote Sales starts only when Main Chat Source is `Remote` and Sales Tracking is enabled. It
reuses the existing pairing credential, access token, Backend endpoint, Discord Bot token, Bot
Gateway connection, and WebSocket session.

## Authorization and hard filters

- Target Guild is the configured Backend Guild and must match the authenticated identity.
- Sales Channel is fixed server-side (`1450076815581380730` by default). It is not a normal WPF
  configuration field.
- The existing bounded authorization lease computes Discord channel overwrites for both the
  authenticated user and Bot. Both must have View Channel and Read Message History.
- Authorization is refreshed periodically. Temporary verification failure suspends delivery;
  revocation stops Sales delivery. Recovery after missed events requires a new bootstrap.

## Bootstrap and publication

- The stream is activated before REST history is fetched, so racing Gateway mutations enter the
  Sales journal.
- REST history is hard-capped at 100 messages. Exactly 100 messages is reported as `Truncated`,
  never silently as complete history.
- Sales uses its own random generation, monotonic sequence, 256-event journal, 256-event outbound
  subscription, and 100-message canonical cache.
- Bootstrap completion applies journal events newer than the capture point before returning the
  snapshot. Resume validates generation, sequence range, and retained history.
- Message create/update/delete are keyed by Discord Message ID. The WPF side upserts into the
  existing `SalesStateEngine`; Local RPC plus Remote therefore remains one domain record.

## Official completion evidence

Canonical Discord REST message objects expose an emoji-level reaction summary and total count.
M9.5 reads that summary only; it never fetches or transports reactor user lists.

Completion marker policy is stable and ID-first:

- custom ID `1451583544295034940`, fallback exact name `SOLD`
- custom ID `1418284521337651321`, fallback exact name `closed`
- if a custom ID exists, the ID alone decides; a wrong ID with a matching name is not a match
- either marker means Sold

Gateway add/remove/remove-all/remove-emoji signals are coalesced for 100 ms by Message ID and
cause a canonical REST refresh. A single reaction-remove signal is not treated as proof that an
emoji is absent, because it represents one user's removal. The coalescer is capped at 256 keys.
Gateway disconnect publishes resync-required instead of clearing trusted Sold state.

## Trust and arbitration

Only `Complete` Remote observations may map absence of both markers to `NotSold`. `Partial` and
`Unavailable` observations never clear Sold. `NotObserved` remains distinct from `NotSold`.

The existing `SalesStateEngine` is the sole Pending/Sold/Deleted state machine. Backend stream
state is only a bounded transport cache; it does not own Sales domain transitions.

While Remote evidence is live and complete for a Message ID, it wins for that ID and UIA remains
shadow/A-B evidence. When Remote is unavailable, revoked, resyncing, or disabled, UIA resumes its
existing role. All evidence is rebased onto one client-side monotonic observation generation, so
the engine sees one ordered stream. Repeated equivalent Remote/UIA evidence is idempotent and
does not create another Sold transition or personal alert.

## Health and diagnostics

Settings displays a safe `Remote Sales` state. Runtime diagnostics record Remote Sales state,
observation count, and Remote/UIA agreement/conflict counts. Logs contain state, coverage, and
counts only; Sales message bodies, Bot tokens, access tokens, and authorization headers are not
logged.

## Security and performance

- No Add Reaction, Remove Reaction, message write, button, command, or Discord write-back path.
- No additional Gateway intents and no Guild Members intent.
- No second Bot token, pairing flow, Discord Gateway, database, broker, media fetch, polling loop,
  or per-message thread.
- Existing DPAPI credential protection, redaction, connection limits, and pairing security remain.
