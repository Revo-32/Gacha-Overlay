# M9.0 LS Overlay Transition Foundation

## Scope and status

M9.0 prepares the existing Gacha Overlay codebase for the future **LS Overlay**
GTA Online companion architecture. It does not switch production data acquisition,
open a backend connection, host a service, authenticate a Bot, or change the UI.
The published `v1.0.0-rc.1` package, executable name, repository name, namespaces,
local data directory, OAuth flow, and release tooling remain legacy-compatible.

## Existing production data paths

### Main Chat and Sales messages

```text
Discord Desktop
  -> Discord local RPC transport/client (Infrastructure)
  -> DiscordConnectionCoordinator (generation, subscriptions, bootstrap)
  -> DiscordMessageNormalizer (raw JSON -> normalized Core patches/mutations)
  -> IOverlayMessageIngress / DiscordMessagePipeline (Core)
  -> DiscordMessageStore
       -> Main Chat: latest 20
       -> Sales source: independent retention/state
  -> WPF presentation coordinators and view models (App)
```

The Core types retain their existing `Discord*` names in M9.0 to avoid mixing a
large mechanical rename with an architecture change. They are application-owned,
normalized records—not Discord.Net, Gateway, REST, or RPC SDK payload types.

### Sales completion evidence

```text
Discord Desktop accessibility tree
  -> WindowsDiscordAccessibilityAdapter (raw Windows/UIA concepts, App)
  -> DiscordUiaSalesReactionObservationSource
  -> ISalesReactionObservationSource (normalized evidence contract, Core)
  -> SalesStateEngine trust rules
  -> SalesPresentationCoordinator -> WPF
```

The UIA source is evidence-only. Raw `AutomationElement`, `AutomationId`, and
`ControlType` values do not cross into Core. UIA is not used to manipulate Discord.

### Settings, health, and diagnostics

- `AppSettings` and `JsonSettingsStore` own persisted configuration and migration.
- `DiscordConnectionStatus`, `SalesSensorHealth`, and `SalesFeatureHealthSnapshot`
  keep connection facts separate from trusted Sales domain state.
- diagnostics use an explicit artifact allowlist and the central
  `SensitiveDataRedactor`; raw Discord message payload/content and protected
  credential storage are excluded.

## Provider seam introduced in M9.0

`IOverlayMessageIngress` is the normalized Chat/Sales-message input boundary.
`DiscordMessagePipeline` implements it, and the active
`DiscordConnectionCoordinator` now depends on the interface rather than the
concrete pipeline. A later remote adapter can translate a versioned LS Overlay
event into the same `DiscordMessageMutation`/snapshot inputs without importing a
Discord SDK into Core or changing WPF presentation.

`ISalesReactionObservationSource` remains the separate completion-evidence
boundary. The current UIA source and test sources expose the same provider
metadata contract. A future trusted backend completion source can implement this
role without weakening the current evidence rules.

`IOverlayDataProvider`, `OverlayDataProviderDescriptor`, and capability flags
describe independently composable provider roles. The catalog marks:

- Discord Local RPC Chat/Sales messages: `Production`
- UIA Sales completion evidence: `Production`
- LS Overlay remote Chat/Sales/Presence/write-back capability: `PreparedOnly`

This is intentionally not one large provider interface. Presence and narrow
write-back will receive their own role contracts when implemented, so Chat does
not acquire unused methods and future categories remain possible.

`OverlayProtocolVersion` and `OverlayEventPosition` reserve only the minimum
version, event-sequence, and bootstrap-generation vocabulary needed before a
remote replay protocol can be designed. M9.0 defines no wire serializer, event
DTO hierarchy, WebSocket connection, bootstrap replay, or raw Gateway envelope.

## Backend boundary

`LSOverlay.Backend` is a headless `net8.0` class-library boundary. It references
only `GachaOverlay.Core` and exposes the prepared remote provider descriptor and
protocol version. It contains no executable host, WPF/Windows dependency,
Discord.Net package, ASP.NET Core dependency, token/configuration handling,
network listener/client, or deployment file. The Windows application does not
reference or instantiate it.

## Coexistence and trust boundary

During and after M9.0, production composition remains:

```text
Local RPC message provider + UIA completion provider -> trusted Core -> WPF
```

The later coexistence shape is:

```text
Legacy mode: Local RPC message provider + UIA completion provider
Remote mode: LS Overlay remote adapters -> normalized Core ingress/source roles
```

Provider selection must be explicit in a later milestone. There is no silent
fallback to cloud, no startup cloud dependency, and no LS Overlay network traffic
in M9.0. Local RPC/UIA are retained because they are the tested public RC path and
because a remote Bot/backend, protocol, pairing model, replay behavior, and
operational deployment do not yet exist.

All external observations are normalized before Core. Transport reachability or
partial evidence never has authority to destroy trusted Sales state. The fixed
Sales rules remain:

- `NotObserved` is not `NotSold`.
- Production completion marker `SOLD` has emoji ID `1451583544295034940`.
- Production completion marker `closed` has emoji ID `1418284521337651321`.
- Either marker means `Sold`.
- A known emoji ID is authoritative; a wrong known ID never falls back to a
  matching-looking name.
- Only when an ID is unavailable may the exact canonical name be used.
- Partial, unavailable, or not-observed evidence cannot revert `Sold`.
- Only trusted, complete evidence that both markers are absent may return a
  retained `Sold` record to `Pending`.

Main Chat generation, transactional channel switching, exact MessageId mutation,
latest-20 retention, CreatedAt then numeric MessageId ordering, and Sales/Main
isolation remain inside the unchanged mature pipeline.

## Backend security and least privilege

The future Bot is a read-oriented overlay provider, not a moderation Bot. It must
never require Discord Administrator, Manage Guild/Channel/Role/Message/Webhook,
kick, ban, or moderation permissions. The expected narrow server permissions are:

- View Channel
- Read Message History
- Add Reactions (only for narrowly scoped Bot-owned Sales status write-back)

Expected Gateway intents are `GUILDS`, `GUILD_MESSAGES`,
`GUILD_MESSAGE_REACTIONS`, `MESSAGE_CONTENT`, and `GUILD_PRESENCES`.
`GUILD_MESSAGE_POLLS` may be considered later only if complete poll updates need
it.

Any future Bot token is server-side only, injected through the deployment
environment or a server secret store. It must never be sent to a Windows client,
committed to source/tests/examples, logged, or included in a diagnostic bundle.
Rich Presence join/spectate/match secrets are also never collected or logged.

this document.

## Branding and compatibility

`ProductIdentity` centralizes the current display name, future display name, and
stable legacy technical/storage name. M9.0 deliberately keeps `GachaOverlay`
namespaces/projects, `%LOCALAPPDATA%\GachaOverlay`, icons, user-visible legacy RC
strings, `GachaOverlay.sln`, release manifest, executable name, ZIP name, tag, and
GitHub remote unchanged. A later migration must define storage/settings continuity
and release-tool changes before changing those identifiers.

## Later migration stages

1. **M9.1 — Discord Bot Backend:** add the headless host, Discord adapter,
   least-privilege configuration, and server-only secret injection; keep it
   isolated from the Windows client.
2. Define small versioned transport DTOs for normalized Chat/Sales/Presence
   events, bootstrap, sequencing, replay, and resync. Never expose raw Gateway
   payloads as the public protocol.
3. Implement authenticated HTTPS/WSS backend transport and bounded client
   adapters, with explicit provider selection and legacy coexistence.
4. Add structured GTA host presence/session presentation and narrowly scoped
   Bot-owned reaction write-back with authorization and audit rules.
5. Only after functional migration, perform a dedicated namespace/project,
   executable, storage, documentation, repository, and release-brand rename.

M9.0 does not start any of these later implementation stages.
