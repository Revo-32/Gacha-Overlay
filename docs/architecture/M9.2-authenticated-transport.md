# M9.2 Authenticated Backend–Client Transport

## Status and scope

M9.1 live Discord validation is complete: Bot login, Gateway Ready, target Guild,
Message, Reaction, Presence, tracked-host normalization, and graceful shutdown all
passed against the real service. M9.2 adds a separately testable remote transport
foundation. It does not activate that transport in the Windows application.

The production WPF path remains Discord Local RPC plus Windows UIA. `ApplicationHost`
does not reference, construct, or start `LSOverlay.RemoteClient`; the HUD, Sales,
Main Chat, onboarding, settings, tray, and persistence behavior are unchanged.

## Hosting and dependency boundaries

One `LSOverlay.Backend` .NET 8 process now hosts the existing Discord
`BackgroundService`, versioned Minimal HTTP endpoints, and a raw WebSocket endpoint.
The development default is `http://127.0.0.1:5188`. A non-loopback deployment must
use HTTPS/WSS, configured outside the repository. No certificate or trust bypass is
included.

`LSOverlay.Protocol` is a platform-neutral `net8.0` contract assembly. It contains no
Discord.Net, ASP.NET Core server type, WPF, UIA, Bot configuration, or raw Discord
object. `LSOverlay.RemoteClient` depends only on that project and the .NET HTTP and
WebSocket clients. Discord.Net remains referenced only by `LSOverlay.Backend`.

Raw WSS was selected instead of SignalR because version 1 has a very small explicit
control protocol: resume, replay, resync, live, heartbeat, and one public Presence
event. Owning those frames directly makes generation/sequence behavior, input bounds,
and replay-to-live cutover auditable without introducing a second hub protocol or its
implicit reconnect semantics.

## Discord-native pairing

The Backend reconciles one target-Guild command:

```text
/lsoverlay pair code:<temporary-code>
```

It reads existing Guild commands and creates or reconciles only the LS Overlay
command; it never bulk-overwrites Guild commands and never registers globally.
Reconciliation runs after the target Guild is available and is safe to repeat after a
Gateway reconnect. A registration failure degrades pairing only; Discord ingestion
and already issued credentials can continue.

Every reply is ephemeral. Interaction responses do not require the Bot's **Send
Messages** channel permission, so the permission ceiling remains View Channel, Read
Message History, and Add Reactions. M9.2 still does not exercise Add Reactions.

The human `UserCode` uses eight non-ambiguous base32 characters (40 bits) and expires
after two minutes. It merely lets a Discord user select a pending request. The
independent `PairingClaimSecret` contains 256 random bits, remains machine-only, is
sent only in `Authorization: LSOPairing ...`, and is stored in the pending in-memory
store only as SHA-256. Possession of the short code alone cannot retrieve a token.
The pending store is thread-safe, limited to 64 entries, lazily reclaims expired or
consumed entries, and allows one claim only.

## Client credentials and authenticated identity

Approval and a valid machine claim issue a new opaque token with at least 256 random
bits. It is independent of the Bot Token, UserCode, and PairingClaimSecret. The
plaintext is returned exactly once and is never persisted by the Backend.

`LSO_STATE_DIRECTORY/client-credentials.v1.json` stores only SHA-256 token hashes and:

- schema version;
- random `ClientInstallationId`;
- approving `DiscordUserId`;
- target `GuildId`;
- created and expiry times.

Credentials expire after 180 days. Issuing for the same installation replaces and
revokes its old credential; one user may have multiple installations. The registry is
bounded at 128 records. It writes a unique temporary file, flushes it, reopens and
validates the complete model, atomically replaces the primary where supported, and
keeps a backup. A valid backup can recover a corrupt primary. If both copies are
invalid, remote authentication fails closed rather than resetting the registry.

After header authentication, application code receives only
`AuthenticatedClientIdentity(ClientInstallationId, DiscordUserId, GuildId)`. It does
not carry the plaintext token. A targeted Discord REST lookup of that single Guild
member is performed for bootstrap and WebSocket connection. Results distinguish
Member, NotMember, and VerificationUnavailable. No full member download or member
cache is used, and `GuildMembers` Gateway Intent remains off. A bounded 128-entry,
five-minute targeted-result cache avoids repeated lookups.

A deployed Backend must mount `LSO_STATE_DIRECTORY` on persistent private storage.
The M9.2 helper intentionally uses and removes an isolated temporary directory.

## Mandatory channel authorization invariant

> Bot-visible does not mean user-visible.

M9.2 publishes no channels, messages, reactions, Sales state, attachments, or media.
For M9.3, a channel may be returned only when both the Bot and the authenticated user
can view it. User evaluation must apply Discord's effective permission order:
`@everyone` Guild permissions, aggregate member roles, Administrator semantics for
the user, the `@everyone` channel overwrite, aggregate role overwrites, the member
overwrite, and thread-specific visibility where applicable. Bot permissions alone
are never an authorization shortcut. Preserving `DiscordUserId` on every connection
is the foundation for that check.

## HTTP API

- `GET /healthz` is unauthenticated and returns only `{ "status": "ok" }`.
- `POST /api/v1/pairings` accepts protocol version and a random installation UUID.
- `GET /api/v1/pairings/{pairingId}` requires `Authorization: LSOPairing <secret>`.
- `GET /api/v1/bootstrap` requires `Authorization: Bearer <client-token>`.
- `/api/v1/stream` requires Bearer authentication before WebSocket acceptance.

Credentials are never accepted from a URL, query string, cookie, body-only fallback,
or WebSocket subprotocol. Credential-like query keys are explicitly rejected. Pairing
creation is limited to 5 requests per remote IP per minute and claim/status to 60,
with queue limit zero. No wildcard CORS or request-body logging is enabled.

## Bootstrap, publication journal, and replay

Bootstrap contains protocol version 1, a unique runtime generation, the latest public
sequence, the authenticated user's Discord ID, and safe tracked-host slots. The
snapshot and sequence are captured under the same synchronization boundary.

The remote publication journal is deliberately separate from the M9.1 internal
Message/Reaction journal. It contains only `host_presence_changed`, is limited to
2,048 events, evicts oldest first, and has a monotonic sequence within one runtime
generation. Thus remote sequences have no gaps caused by unpublished internal data.

The client requests subprotocol `ls-overlay.v1`, then sends version, generation, and
`AfterSequence`. A mismatched generation, evicted cursor, or future cursor produces
`resync_required`. For a valid cursor, the server copies replay through a cutoff and
registers the connection for post-cutoff events while holding the journal lock; it
then releases the lock before socket I/O, sends replay, drains the bounded post-cutoff
queue, and enters Live. This prevents both loss and duplication across the cutover.

Inbound text is capped at 16 KiB. Binary, malformed, unsupported-version, and unknown
control frames receive a controlled close. Each client has a fixed 256-event outbound
queue and one send loop. A full queue disconnects that slow client without blocking
the Discord Gateway. Limits are 64 total sockets and 2 per installation.

.NET 8 protocol heartbeats run every 30 seconds and require acknowledgement within
75 seconds. Heartbeats are control-plane frames: they do not consume sequence numbers,
enter replay, or create HUD work.

## GTA Presence end to end

The only M9.2 public application event follows this path:

```text
Discord.Net RichGame
  -> GtaPresenceNormalizer
  -> TrackedHostPresenceSnapshot
  -> remote publication journal
  -> LSOverlay.Protocol
  -> LSOverlay.RemoteClient
  -> LSOverlay.TransportProbe
```

The verified profile remains Grand Theft Auto V Enhanced, application ID
`1329870933695135785`, Playing, state GTA Online. Population comes only from the
structured `RichGame.Party` current/capacity values after `0 <= current <= maximum`.
The real 11/32 shape is preserved exactly in bootstrap and live events. The protocol
uses a stable host slot rather than a Discord user ID and exposes no Rich Presence
secret or raw SDK payload. Unchanged normalized Presence is not republished.

## Remote client and local validation

`LSOverlay.RemoteClient` uses `HttpClient` and `ClientWebSocket`, enforces TLS outside
loopback, sets Authorization headers, handles bootstrap/resume/resync, acknowledges
heartbeats, and exposes normalized Presence. Its single-flight reconnect uses bounded
1/2/4/8/16/30-second backoff plus small jitter. Authentication failure stops the loop;
resync obtains a fresh bootstrap. The future Windows integration must protect its
token with current-user DPAPI. M9.2 stores the probe token in process memory only.

From the repository root, the live check is one command:

```powershell
.\tools\dev\run-ls-m92-local.ps1
```

The helper securely prompts for Guild ID, optional tracked-host IDs, and Bot Token. It
starts only the Backend with those variables, immediately removes the Bot Token from
the parent environment, waits for Discord command readiness, and only then starts the
Probe. The Probe therefore cannot inherit the Bot Token. It displays the UserCode,
keeps claim and access credentials off the console, performs pairing/bootstrap/WSS,
and prints safe host state. `finally` clears every environment value, signals graceful
Backend shutdown, waits for exit, and removes the temporary state directory.

## Security and observability

Authorization headers, access tokens, pairing claim secrets, Bot Token, credential
hashes, raw Discord payloads, User IDs as metric labels, and request bodies are not
logged. The shared redactor recognizes access-token, pairing-secret, Bearer, and
LSOPairing terminology and remains idempotent. Metrics are fixed process-local
counters without identity labels. The health response contains no IDs, counts, token
status, permissions, storage paths, or exception details.

## Deferred to M9.3 and later

M9.3 should add an authenticated Remote Chat Provider: per-user authorized channel
catalog, targeted member/role permission evaluation, remote Main Channel selection,
recent-20 bootstrap, create/update/delete, and complete official Discord message
normalization (display name, content/custom emoji, attachments, embeds, stickers,
forwarded snapshots, replies, components, and useful poll data). Media remains direct
client CDN metadata rather than a Backend proxy. Existing `MainChatStore` semantics
should be reused while Local RPC coexists until the remote path is live-verified.

Deployment, production TLS/domain, WPF pairing UI, DPAPI persistence, remote Sales,
reaction write-back, Add Reactions calls, UIA/Local RPC removal, branding/EXE/repository
renames, and release creation remain out of scope.
