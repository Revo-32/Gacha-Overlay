# M9.4 Production Remote Chat Integration

## Product contract

- Legacy Local RPC remains the default main-chat source.
- Remote is an explicit opt-in main-chat source.
- Sales tracking remains on the existing Local RPC/UIA path in both modes.
- Existing users are not migrated automatically.
- Returning to Legacy does not require a working Remote endpoint.

## Settings and protected state

Schema 12 adds only non-secret settings:

- `ChatSource`
- `RemoteBackendBaseUrl`
- `RemoteSelectedChannelId`

The Remote access token is stored separately in `remote-access-token.dat`, protected
with Windows DPAPI `CurrentUser` scope and M9.4-specific optional entropy. The file
is written atomically. Pairing codes and access tokens are not written to logs,
settings, or diagnostic bundles.

Plain HTTP is accepted only for endpoints allowed by the shared transport security
policy (loopback development). Non-loopback production endpoints require HTTPS.

## Pairing lifecycle

1. WPF requests a pairing from the configured backend.
2. The user receives a short code and the localized instruction
   `/lsoverlay pair code:<code>`.
3. WPF polls the claim endpoint until approval, expiry, or cancellation.
4. An approved token is protected immediately before any authenticated session starts.
5. Unpair/forget stops the session, clears the protected token, and clears the Remote
   channel selection.

An unreadable token is fail-closed. Authentication rejection requests repair or
re-pairing but does not silently delete the credential. Network failure preserves it.

## Production session

When and only when Remote is selected, the coordinator:

1. loads the protected token;
2. authenticates and bootstraps the current identity;
3. loads the server-authorized channel catalog;
4. validates the persisted channel against that catalog;
5. bootstraps recent messages;
6. opens the authenticated stream;
7. maps recent/create/update/delete through `IOverlayMessageIngress` and the existing
   `DiscordMessagePipeline`/`DiscordMessageStore` semantics.

The store retains the latest 20 messages, orders by creation time and numeric ID,
does not reorder an update, and deletes only the exact message ID.

Reconnects use bounded exponential backoff with jitter. A stale or unauthorized
channel selection is cleared without crashing. The health model distinguishes pairing,
authentication, connection, bootstrap, live, reconnecting, authorization unavailable,
access revoked, disconnected, and error states.

## Transactional channel switching

The selector exposes only names returned by the authenticated channel catalog. A switch
first obtains the new channel bootstrap, then asks the live stream to switch. The old
channel remains active until `chat_ready` arrives for the new channel. Only then is the
new channel persisted and presented as selected.

## Presentation boundary

The WPF/Core boundary uses application-owned normalized models; it has no Discord.Net
dependency and does not render raw protocol JSON. Remote messages reuse the established
HUD typography, media policy, caching, and responsive layout.

Supported read-only presentation includes:

- text, Unicode emoji, and custom emoji;
- attachments and HTTPS images;
- stickers;
- forwarded text and forwarded media;
- embed text and media;
- reply context when resolved content is available;
- component labels without interaction/writeback;
- poll question/answers;
- voice-message duration and attachment context.

Media continues to be fetched by the client through the existing bounded media service;
the backend does not proxy media bytes.

## Diagnostics and shutdown

The settings UI shows localized Remote health, protected-credential availability, and
authorized-channel count. Diagnostic artifacts record health and configuration booleans,
but omit token contents, pairing codes, endpoint paths, and selected channel IDs.

Shutdown cancels pairing and reconnect loops, closes the stream, detaches ingress/client
events, and disposes the Remote client before the HUD and logging infrastructure finish.

## Validation boundary

Automated tests use fake clients and local files only. They do not contact production
Discord or a production backend. Actual user pairing and live Discord validation remain
an explicit post-build checklist.
