## Core 중심 Backend 설계

목표 경로는 `Core EXE → HTTPS 인증/Core API → 기존 권한·Chat/Sales/Presence 서비스 → Core 의미 DTO`다. 개발 bridge를 공개 노출하거나 전역 연결 제한만 늘려 운영 서비스로 사용하지 않는다.

1. **기존 보안 자산 유지:** OAuth, 사용자별 자격증명, trusted proxy/client-IP, rate limiting, 권한 철회 및 판매 도메인 검증을 재사용한다. 새 봇이나 운영 자격증명 복제는 전제하지 않는다.
2. **세션 격리:** 현재 개발 bridge의 전역 `activeMedia`/채널 변경 delegate를 사용자별 수명으로 이동한다. 한 사용자의 채널 변경·끊김·미디어 취소가 다른 사용자에 영향을 주지 않아야 한다.
3. **서버 중심 의미 처리:** Chat/Sales 상태와 파싱은 서버에서 처리하고 C++는 최종 텍스트/이미지 배치와 입력을 담당한다. 운영 Backend 자신을 다시 HTTPS로 호출하는 개발 중계 구조는 정식 기본 경로로 삼지 않는다.
4. **미디어 분리:** opaque ID별 사용자/메시지 권한 확인과 변환 전후 검사를 유지한다. 변환 worker는 비공개·자원 제한·폐기 가능한 캐시를 사용하며 Chat/heartbeat와 독립적으로 동작한다.
5. **Core 전용 계약:** protocol capability/version을 명시하고 미지원 버전은 안전하게 안내한다. Full 전용 기능은 신규 Core snapshot에 넣지 않는다. 현재 필요한 기존 서비스와 제거 가능한 Full 전용 부분을 분리한 뒤 정리한다.

## 실행 순서와 완료 조건

1. 첫 정식판의 판매 완료·되돌리기 포함은 사용자 승인 완료. 실사용 검증 결과를 확인한다.
2. 정식 Core endpoint와 EXE 기본 시작 경로를 구현한다. 개발/합성 모드를 배포 경로에서 분리한다.
3. 격리된 M8 환경에서 최소 2개 사용자 세션의 권한/데이터/채널 분리, 인증 만료/철회, 서버 재시작, 미디어 실패 시 채팅 독립성을 검증한다. 판매 조작을 포함하면 서버 권한·중복 입력·공식 상태 read-back도 검증한다.
4. 확정 버전으로 내부 RC를 만든다. EXE·필수 폰트·라이선스·안내만 포함하고 PDB·소스·개발 launcher·계측 파일·캐시·인증정보를 제외한다. 깨끗한 사용자 환경에서 SSH/.NET 개발 도구 없이 실행을 확인한다.
5. 최종 운영 배포 대상·변경 설정·상태 보존·이전 M8 이미지 롤백 절차를 확정하고, 사용자가 승인한 Core 릴리즈 범위에서 운영 전환한다. 범위 밖 파괴적 변경은 별도 확인한다. Railway를 복구 수단으로 사용하지 않는다.
6. 운영 인증 연결과 실제 동작 확인 후 정식 배포한다. 사용자는 조건 통과 후 릴리즈 진행을 승인했으므로 같은 승인을 반복 요청하지 않는다. 기존 공개 태그·자산을 덮어쓰지는 않는다.
7. 기본판 지원 종료와 Core 설치/이전 안내를 공지한다. 설정/로그인을 몰래 가져오지 않으며, 기존 API 정리는 전환 확인 후 별도 단계로 수행한다.

## 이번 준비 단계에서 하지 않은 작업

운영 배포, DNS/Cloudflare 변경, 기존 Backend API 삭제, 기본판 배포물 삭제, 버전 변경, Git 커밋/푸시/태그/공개 릴리즈는 수행하지 않았다. 개발 실행본을 정식 배포물로 포장하지 않았다.

사용자는 첫 정식판에 **판매 완료·되돌리기 조작 포함**, 조작 검증 및 필수 릴리즈 조건 통과 후 공개 릴리즈 진행을 승인했다. 기존 읽기 전용 개발 검증은 실제 판매 쓰기 검증이 아니다. 임의의 실제 판매글을 테스트 목적으로 변경하지 않으며, 사용자 지정 대상 또는 사용자가 직접 실행한 조작으로 확인한다.
